# 0007: Transport abstraction, registry and shared transport building blocks

- **Status:** Accepted (maintainer sign-off 2026-09-29)
- **Accepted with defaults:** every open question below was accepted with the recommended default given next to it. Needs-verification items stay open and are resolved in the implementing WPs; a result that invalidates a default is handled by a superseding ADR.
- **Date:** 2026-09-29
- **Plan decision:** D4 in [`plugin-hardening-and-fab-readiness.md`](../roadmap/plugin-hardening-and-fab-readiness.md) §3
- **Related:** [ADR 0002](0002-webrtc-and-moq-in-first-fab-release.md) (WebRTC add-on, interface version), [ADR 0003](0003-core-library-delivery-to-plugin.md) (`Open3DStreamCore`), [ADR 0004](0004-credentials-and-secret-transport-options.md) (secret keys, `FO3DSecretStore`), [ADR 0005](0005-wire-resync-and-loss-contract.md) (delivery guarantee, new-peer signal), [ADR 0006](0006-test-module-layout-and-fakes.md) (conformance suite, fakes), ADR 0008 (D5), ADR 0009 (D8), ADR 0010 (D9); feeds WP-A1, WP-S5, WP-A5, WP-F3, WP-F11, WP-D3

**Recommendation in one line:** move `IOpen3DSender`, `IOpen3DReceiver` and **one** transport registry into `Open3DShared` (no new module). A transport registers one immutable descriptor (factories, capabilities, option schema, config functions) and gets a handle back. The registry tracks live instances and drains them before a module unloads. Every method has a written threading contract, errors are a result type, and an exported interface version lets the WebRTC add-on refuse a mismatched host. The queue, worker, receive demux, audio sink guard, host:port parsing, backoff and FFI loader are written once in Shared, and transports migrate one per PR behind forwarding shims kept for one release.

## Context

**Two registries, two customization maps, duplicated line for line (SHR-12, SND-23, RCV-28).**
- Factories: `O3DTransport::RegisterSender/CreateSender` (`Plugin/Source/Open3DSender/Public/O3DSenderRegistry.h:9-18`, a global `FCriticalSection` plus `TMap` at `Private/O3DSenderRegistry.cpp:10-11`) and the receiver copy (`Open3DReceiver/Private/O3DReceiverRegistry.cpp`).
- Customizations: `O3DSender::RegisterTransportCustomization` (`Open3DSender/Private/O3DSenderTransportCustomization.cpp:10-18`) and the receiver copy.
- Pickers list customization names (`O3DSenderComponent.cpp:723`, `O3DReceiverSource.cpp:424`), while instances come from the factory map (`O3DSenderTransportController.cpp:21`, `O3DReceiverSource.cpp:325`). The two can disagree.
- `FindTransportCustomization` returns a raw pointer into the map after the lock is released (`O3DSenderTransportCustomization.cpp:26-30`; receiver `:28-32`), and callers invoke its `TFunction`s (`O3DSenderComponent.cpp:341`, `O3DReceiverSource.cpp:480`) (RCV-27).
- `Open3DShared/Public/O3DTransportRegistry.h:5-11` `__has_include`s paths that never resolve, so it is empty.
- Every transport registers four times in `StartupModule` (for example `Open3DTransportSocketsModule.cpp:35-91`).

**No lifetime contract (SHR-13, TRF-14).** `ShutdownModule` only unregisters (`Open3DTransportSocketsModule.cpp:96-108`). Live instances whose code lives in the transport DLL stay referenced by components. WebRTC registers factories even when `livekit_ffi.dll` failed to load (`Open3DTransportWebRTCModule.cpp:617-623`) and calls `FreeDllHandle` with no instance check (`:777-781`). MoQ returns early on load failure (`Open3DTransportMoQModule.cpp:561-565`), which is the correct pattern.

**Interface shape (SHR-12, SHR-14).**
- `IOpen3DSender` (`Open3DSender/Public/O3DSenderInterface.h:27-90`) returns `bool` everywhere. `SendSerialized` has a default body that returns false (`:73-77`). `Send(const O3DS::SubjectList&)` (`:45`) is off the normal path (`O3DSenderComponent.cpp:363-385` only calls `SendSerialized`).
- `IOpen3DReceiver` (`Open3DReceiver/Public/O3DReceiverInterface.h:22-42`) has `Poll()` and `SetConsumer`; neither says which thread calls it.
- `FO3DTransportStats` (`Open3DShared/Public/O3DTransportTypes.h`, end of file) has no state, error or queue-depth field.
- Neither interface has a version or a capability query.

**What each `SendSerialized` does today** (the D5 worker will call it):

| Transport | Behaviour | Evidence |
|---|---|---|
| TCP | copies into a framed buffer and enqueues; rejects the newest when full | `SocketsTcpSender.cpp:205-213`, `:553-588` |
| UDP | calls `SendTo` synchronously under `OwnerGuard->Lock` (TRB-20) | `SocketsUdpSender.cpp:211-240` |
| NNG | enqueues; the worker requeues at the tail on `EAGAIN` and sleeps (TRB-34) | `NngSender.cpp:294-315`, `:533-545` |
| MoQ | enqueues into its own MPSC queue | `MoQSender.cpp:315-331`, `MoQSender.h:121` |
| Loopback | enqueues into the in-process channel | `LoopbackSender.cpp:175-189` |
| WebRTC | calls `lk_send_data_ex` inline on the caller's thread, behind a heuristic backpressure estimate (TRF-5) | `WebRTCSender.cpp:842-935` |

Four transports carry their own `TQueue<..., EQueueMode::Mpsc>` (TCP `SocketsTcpSender.h:104`, NNG `NngSender.h:83`, MoQ `MoQSender.h:121`, Loopback `LoopbackChannel.h:51`). TCP and NNG account bytes with a non-atomic load-then-store (`SocketsTcpSender.cpp:517-518`, `:564-580`; TRB-3).

**Audio sinks (T2).** Sockets hands the sink a `TSharedPtr` to an `OwnerGuard { FCriticalSection Lock; Owner* }` (`SocketsTcpSender.h:28-32`, `SocketsTcpSender.cpp:48-76`). That fixes the use-after-free that Loopback, NNG, WebRTC and MoQ still have (TRB-30, TRB-35, TRF-1). But the same lock is held across the whole encode on the audio thread and across `Socket->Send` on the worker (`SocketsTcpSender.cpp:523-533`; TRB-10), so copying the guard as-is would copy the contention. The sink base `FO3DSenderAudioSinkBase` lives in Open3DSender (`Open3DSender/Public/O3DSenderAudioSinkBase.h:11`).

**Receive side.** TCP, UDP and NNG each carry a copy of the demux (`SocketsTcpReceiver.cpp:405-492`, `SocketsUdpReceiver.cpp:389-476`, `NngReceiver.cpp:487-582`; TRB-38). Each copies the payload into a new `TArray` only because `ISerializedFrameConsumer::SubmitFrame` takes `const TArray<uint8>&` (`Open3DShared/Public/SerializedFrameConsumerRegistry.h:20`; SHR-16). Every receiver calls `SubmitFrame` from inside `Poll()`, and `Poll()` runs on the game thread from `FO3DReceiverSource::Tick` (`O3DReceiverSource.cpp:278-285`). `FSerializedFrameConsumerRegistry` is never populated (SHR-24). MoQ holds the consumer weakly, WebRTC strongly (TRF-38).

**Config.** `FO3DTransportConfig` carries LiveKit-only fields (`O3DTransportTypes.h:66-99`, SHR-36) and free-form `FString Transport/Role`. `ConfigureTransport` takes `const UO3DSenderComponent*` (`O3DSenderTransportCustomization.h:15`), so every transport module depends on Open3DSender and Open3DReceiver (`Open3DTransportLoopback.Build.cs:28-29`, `Open3DTransportNNG.Build.cs:59-60`, `Open3DTransportWebRTC.Build.cs:86-87`, MoQ `:136-137`, Sockets `:35-40`).

**Constraints from accepted ADRs.**
- 0002: the add-on uses only exported API and needs an interface version checked at `StartupModule`.
- 0003: the core is the `Open3DStreamCore` module.
- 0004: `SecretOptionKeys`/`SecretEnvVars` on the customizations, `FO3DSecretStore` and `O3DRedact` in Shared; a typed config must keep "declared secret, resolved from the store, never serialized".
- 0005: `EO3DDeliveryGuarantee` in Shared, `GetDeliveryGuarantee` on the customization "moves to the capability query with the same values", and `IOpen3DSender::SetPeerJoinedCallback`.
- 0006: fakes are registered through the registry under unique names; the conformance suite enumerates registered transports and needs concurrent `SendSerialized` to be safe.

## Decision drivers

1. Memory safety across module unload and across audio, FFI and worker threads (T2).
2. The add-on plugin compiles against a small, exported, versioned API and fails cleanly on a mismatch.
3. One place to fix queue, demux and sink bugs (T5); net transport code goes down.
4. No per-frame allocation or lock contention added on the send and receive paths.
5. Incremental: each PR leaves every transport working and the conformance suite green.

## Options considered

### Where the abstraction lives
- **A. `Open3DShared` (chosen).** Shared already holds `FO3DTransportConfig`, the unified envelope, the audio codec and the consumer interface, and 0004 and 0005 already put `FO3DSecretStore`, `O3DRedact` and `EO3DDeliveryGuarantee` there. Transports then depend on Shared (and `Open3DStreamCore` where they use core code) and no longer on Sender or Receiver. No new module. Con: Shared grows by about 1,500 lines.
- **B. New `Open3DTransportCore` module.** Cleaner name, but Shared would then hold only audio and metrics helpers, both of which the transport core needs, so the split adds a module (twelve with 0003, 0006 and D9) without removing a dependency edge. Rejected.
- **C. Keep the interfaces in Sender and Receiver, merge only the registries.** Keeps the Sender/Receiver edge from every transport and from the add-on. Rejected.

### Registry shape
- **R1. One registry of immutable descriptors, one per transport name, returned as `TSharedPtr<const>` (chosen).** Fixes RCV-27 and RCV-28 by construction.
- **R2. A templated `TO3DFactoryRegistry<T>` per role (SHR-12's suggestion).** Removes the copy-paste but keeps factories and customizations apart.

### Error model
- **E1. `FO3DTransportResult { EO3DTransportError Code; FString Message; }` for lifecycle calls, a plain enum for per-frame calls (chosen).** No `FString` allocation per frame.
- **E2. `TValueOrError`.** Equivalent, but its UE 5.7 header and API are **needs-verification** (Q1), and it gives no advantage for `void` results.

### Config
- **K1. Typed per-transport `UStruct`s (`FInstancedStruct`).** Blueprint-friendly, but an asset saved with a struct from the add-on fails to load its settings when the add-on is disabled, and existing `TransportOptions` maps need migration.
- **K2. Keep the persisted `TMap<FString,FString>`, add a declared option schema with typed, validated accessors (chosen).** Assets stay loadable without the transport module. The schema is also the data the D9 editor module builds widgets from, and its `Secret` type is the typed form of 0004's `SecretOptionKeys`.

## Decision

**1. Home and module graph.** `IOpen3DSender`, `IOpen3DReceiver`, `ISerializedFrameConsumer`, the registry and the building blocks live in `Open3DShared/Public/Transport/`, exported with `OPEN3DSHARED_API`. Transport modules depend on `Open3DShared` (and `Open3DStreamCore` if they include core headers); they drop Open3DSender and Open3DReceiver. Sender and Receiver keep depending on Shared.

**2. Interface version.** `Open3DShared/Public/Transport/O3DTransportApiVersion.h` defines `O3D_TRANSPORT_API_VERSION` (an integer). `O3DTransport::GetHostApiVersion()` is an exported function whose name and signature never change. Add-ons compare the host value with their compile-time value in `StartupModule` and do not register on a mismatch (ADR 0002). `FO3DTransportDescriptor::ApiVersion` carries the compile-time value and the registry rejects mismatches as a second check. **Bump rule:** any change to a public header under `Transport/` that alters a class layout, a vtable, a descriptor field or a documented threading rule. WP-F11 introduces version 1 before this ADR's code lands; WP-A1 PR 1 moves to 2.

**3. The interfaces.** Threading rules are part of the contract and are written in the header next to each method.

| `IOpen3DSender` | Called from | Contract |
|---|---|---|
| `Initialize(const FO3DTransportConfig&) -> FO3DTransportResult` | game thread | non-blocking; validates config |
| `Start() -> FO3DTransportResult` | game thread | non-blocking; connects on the transport worker (WP-A5) |
| `Stop()` | game thread | idempotent; non-blocking; safe while `SendSerialized` or an audio sink call is in flight; later sends return `NotRunning` |
| `SendSerialized(FO3DSendPayload&&) -> EO3DSendResult` | any thread (the D5 pipeline worker in practice) | pure virtual; thread-safe; never blocks; takes ownership of the bytes |
| `Tick(float)` | game thread | upkeep only; never blocks |
| `GetStats()`, `GetConnectionState()` | any thread | lock-free snapshot |
| `CreateAudioSink(...)` | game thread | returns a sink that obeys item 7 |
| `SetPeerJoinedCallback(TFunction<void()>)` | game thread, before `Start` | as ADR 0005 (vi): callback may fire on any thread |
| `SetStateChangedCallback(TFunction<void(EO3DConnectionState, const FO3DTransportResult&)>)` | game thread, before `Start` | callback may fire on any thread; must not call back into the transport |

`FO3DSendPayload { TArray<uint8> Bytes; FName Subject; double CaptureTimeSec; bool bFullSync; }`. `EO3DSendResult { Queued, DroppedBackpressure, NotRunning, NotConnected, Invalid }`. The D5 worker uses `bFullSync` plus a `DroppedBackpressure` result to request the next full sync early. `Send(const O3DS::SubjectList&)` is deprecated in PR 1 and deleted in PR 5 (also removes the core dependency ADR 0002 blocker 2 mentions).

| `IOpen3DReceiver` | Called from | Contract |
|---|---|---|
| `Initialize`, `Start`, `Stop` | game thread | as the sender; `Start` without a consumer returns `NoConsumer` |
| `SetConsumer(TSharedPtr<ISerializedFrameConsumer>)` | game thread, before `Start` | the receiver holds a **strong** reference and releases it in `Stop` (TRF-38) |
| `Poll() -> int32` | game thread | bounded work (TRB-18); the only place the consumer is called |
| `SetAudioSink(...)` | game thread | the sink may be called on any thread |
| `GetStats()`, `GetConnectionState()` | any thread | lock-free snapshot |

`ISerializedFrameConsumer` becomes `SubmitFrame(FName Subject, TConstArrayView<uint8> Bytes, double ReceiveTimeSec)` (view valid for the call only) plus `SubmitFrameOwned(FName, TArray<uint8>&&, double)` whose default forwards to the view form. Consumers are called only from `Poll()`, on the thread that calls `Poll()`. SHR-16 suggested "the transport worker thread"; this ADR keeps the Poll thread because every receiver already delivers there and the receiver source's gate is single-threaded (`O3DReceiverSource.cpp:286-289`). `FSerializedFrameConsumerRegistry` is deleted (SHR-24).

`FO3DTransportResult { EO3DTransportError Code; FString Message; bool IsOk() const; }` with codes `None, InvalidConfig, NoConsumer, NotRunning, ResourceUnavailable, AddressInUse, ConnectFailed, AuthFailed, Timeout, Unsupported, Internal`. `EO3DConnectionState { Idle, Connecting, Connected, Reconnecting, Failed }`. `FO3DTransportStats` gains `State`, `SendErrors`, `ReceiveErrors`, `PendingFrames`, `PendingBytes`.

**4. The descriptor and registry.**
```cpp
struct FO3DTransportDescriptor {                // immutable after Register
  FName Name; FText DisplayName; uint32 ApiVersion; FName OwningModule;
  TFunction<TSharedPtr<IOpen3DSender, ESPMode::ThreadSafe>()>   CreateSender;    // optional
  TFunction<TSharedPtr<IOpen3DReceiver, ESPMode::ThreadSafe>()> CreateReceiver;  // optional
  TFunction<FO3DTransportCapabilities(const FO3DTransportConfig&)> GetCapabilities;
  FO3DTransportOptionSchema SenderOptions, ReceiverOptions;     // item 8; drives D9 widgets
  TFunction<void(const FO3DTransportOptionsView&, FO3DTransportConfig&)> ConfigureSender, ConfigureReceiver;
};
```
- `FO3DTransportCapabilities { bool bSend, bReceive, bAudioSend, bAudioReceive, bBidirectional, bPeerJoinSignal; EO3DDeliveryGuarantee Delivery; int32 MaxPayloadBytes; }`. `Delivery` takes over ADR 0005's `GetDeliveryGuarantee` with the same per-transport values.
- `ESPMode::ThreadSafe` is written explicitly everywhere (SHR-12).
- `FO3DTransportRegistry::Get()` is owned by the Open3DShared module object. `Register(TSharedRef<const FO3DTransportDescriptor>) -> FO3DTransportRegistration` (a move-only handle whose destructor unregisters). `Find(FName) -> TSharedPtr<const FO3DTransportDescriptor>`. `GetNames(EO3DTransportRole)` lists only entries that have a factory for that role (RCV-28).
- Mutation and `Create*` are game-thread-only (`check(IsInGameThread())`). `Find` and `GetNames` are any-thread under an `FRWLock` read lock. Factories and config functions are always invoked outside the lock, as `O3DSenderRegistry.cpp:74-89` already does.
- `OnTransportsChanged` fires after each register and unregister so pickers refresh.
- A transport registers only after its dependencies (FFI DLL, `moq_init`) succeeded (TRF-14).

**5. Lifetime and unload (SHR-13, TRF-14).**
- `Create*` wraps each instance's weak reference in a per-name live list.
- Unregistering broadcasts `OnTransportUnregistering(FName)`. The sender transport controller and the receiver source subscribe, call `Stop()` and drop their references. The registry then calls `Stop()` on anything still alive and logs an Error with the remaining count, naming the owner if known.
- `FO3DFfiLibrary` (item 7) refuses `FreeDllHandle` while its transport's live count is non-zero and leaves the DLL loaded until process exit instead.
- Whether UE shuts transport modules down before or after world teardown at editor exit and during Live Coding is **needs-verification** (Q2); the drain makes either order safe for our own references.

**6. Global state (SHR-38).** No injected runtime context in v1: nothing needs per-PIE isolation, and SHR-38 rates it L. What remains global, and why:
- the transport registry and `FO3DSecretStore` (0004): process-wide by nature; module-owned, created in `StartupModule`, destroyed in `ShutdownModule`;
- `FO3DPerformanceMetrics`: an aggregate diagnostic; transports own their own counters (WP-S10) and publish into it;
- `FO3DAudioBus`: game-thread-only, enforced with `check` (SHR-10);
- console variables and commands: module-scoped (WP-A6).
- Deleted: `FSerializedFrameConsumerRegistry`, the `O3DTransportRegistry.h` umbrella, the `O3DBuildFlags` cache (WP-F2).
- Each keeps a `ResetForTesting()` for the 0006 suite.

**7. Shared building blocks (`Open3DShared/Public/Transport/`).**
- **`FO3DSendQueue` plus `FO3DTransportWorker`.** Bounded MPSC queue of typed items (mocap bytes, encoded audio, control), with `fetch_add`/`fetch_sub` byte and count accounting (TRB-3). Soft cap: the worker drops the oldest mocap items while over the cap. Hard cap (twice the soft cap): producers get `DroppedBackpressure`. Audio and control items are never dropped for mocap. Optional age limit (TRB-14). The worker is an `FRunnable` with a wake event that also runs connect, disconnect, reconnect and FFI lifecycle calls (TRF-7, WP-A5) and a `FO3DReconnectPolicy` backoff (exponential, jitter, reset on success; TRB-4, TRF-6, TRF-20). UDP and WebRTC move their sends onto it (TRB-20).
- **`FO3DUnifiedReceiveDemux`.** Classifies bytes by the D8 header rules (ADR 0009), routes mocap to the consumer without copying and audio to a per-stream decoder map keyed by `(SourceGuid, StreamLabel)` with an LRU cap (SHR-15). Replaces the three copies and closes TRB-37.
- **`FO3DSenderAudioSinkBase` (moves from Open3DSender) with `FO3DAudioPublishState`.** The sink holds a `TSharedPtr<FO3DAudioPublishState, ESPMode::ThreadSafe>`, never the sender. The state holds an `FRWLock`, a `bOpen` flag, the per-stream encoders and a handle to the transport's `FO3DSendQueue`. `SubmitPcm` takes the read lock, returns if closed, encodes into sink-local scratch, and enqueues. `Stop()` takes the write lock, clears `bOpen`, and only then releases handles. No lock is ever held across a socket or FFI call, and FFI audio publish runs on the transport worker (TRF-1, TRB-10, TRB-30, TRB-35). The receiver side gets the mirror `FO3DReceiverAudioSinkBase` holding immutable metadata only (RCV-1).
- **`O3DTransportOptions`**: strict `ParseHostPort` (port 1 to 65535, bracketed IPv6) and typed getters; hostname resolution happens on the worker (`GetAddressInfoAsync`, **needs-verification**, Q3) (TRB-26, SHR-9: delete `NormalizeTcpUrlHostPort`).
- **`FO3DFfiLibrary`**: finds the DLL relative to the *owning* plugin (fixes ADR 0002 blocker 1 and TRF-28), reports load status, and implements the unload rule in item 5.
- Shared audio (de)serializers with one header reader and writer (SHR-35).

**8. Typed config (K2).** `FO3DTransportConfig` keeps `FName Transport`, `EO3DTransportRole Role`, `Uri`, `StreamId`, `Audio`, `Secrets` (0004) and gains `FO3DTransportOptionsView Options`. The LiveKit fields and `bPersistToken` are removed (SHR-36); WebRTC declares them in its schema. `FO3DTransportOptionSchema` is an array of `{Key, DisplayName, Tooltip, Type (String, Int, Float, Bool, Enum, Url, Secret), Default, Min, Max, EnumValues, VisibleWhen, bRestartOnChange}`. Keys stay namespaced (`webrtc.url`), and switching transports no longer clears other transports' keys (SND-35). A `Secret` entry is the typed form of 0004's `SecretOptionKeys`; its env var name moves into the entry. Persistence, the store and redaction behave exactly as 0004 says. Role names and transport names use the registered names everywhere (TRB-27).

**9. Migration.** The old headers (`O3DSenderInterface.h`, `O3DSenderRegistry.h`, `O3DSenderTransportCustomization.h` and the receiver equivalents) stay for one release as forwarding shims marked `UE_DEPRECATED` (**needs-verification** of the 5.7 macro, Q1). The old `RegisterSender` plus `RegisterTransportCustomization` pair builds a descriptor internally, so the add-on built against the previous release keeps working. Shims are deleted in the release after.

## Consequences

- **Easier:** one fix for each queue, demux and sink bug; transports and the add-on depend on Shared alone; the conformance suite (0006) and the D9 editor module both enumerate one registry; the editor gets a data schema instead of per-transport Slate code.
- **Harder:** a large, staged migration (WP-A1, size L); the interface version must be bumped with discipline; the add-on must be rebuilt per release (already true under 0002).
- **Constrains:** D5 calls `SendSerialized` from its worker and relies on "non-blocking, thread-safe". D9 builds panels from `FO3DTransportOptionSchema`. ADR 0004's per-customization fields become schema entries with unchanged semantics. ADR 0006's fake transports register descriptors. FFI transports keep the per-instance function tables (0006 F2) behind the worker.
- **Not decided here:** receive-side threading for UDP beyond bounded `Poll` (TRB-18 stays in WP-S2).

## Implementation outline

WP-A1 PR sequence; each PR keeps all transports working and the conformance suite green.
1. **Interfaces and registry (SHR-12, SND-23, RCV-27, RCV-28, SHR-24).** New `Open3DShared/Public/Transport/{O3DTransportApiVersion.h, O3DSenderInterface.h, O3DReceiverInterface.h, O3DTransportRegistry.h, O3DTransportTypes.h}` and `Private/Transport/O3DTransportRegistry.cpp`. Old Sender/Receiver headers become shims; delete `Open3DShared/Public/O3DTransportRegistry.h` and `SerializedFrameConsumerRegistry.*`. Sender and Receiver call the new registry (`O3DSenderComponent.cpp:341`, `:723`, `O3DSenderTransportController.cpp:21`, `O3DReceiverSource.cpp:325`, `:424`, `:480`, `O3DReceiverSourceFactory.cpp:263`, `:392`, `O3DSenderComponentCustomization.cpp:389`, `:475`).
2. **Lifetime (SHR-13, TRF-14).** Live lists, `OnTransportUnregistering`, controller and source subscriptions, `FO3DFfiLibrary`; WebRTC and MoQ modules adopt it (`Open3DTransportWebRTCModule.cpp:614-785`, `Open3DTransportMoQModule.cpp:558-597`). Lands with WP-F3.
3. **Results, state, capabilities (SHR-14).** `FO3DTransportResult`, `EO3DSendResult`, `FO3DSendPayload`, connection state and callbacks, `FO3DTransportCapabilities` (absorbs 0005's `GetDeliveryGuarantee`), `SendSerialized` pure virtual.
4. **Building blocks, one transport per PR.** Order: Loopback (smallest), TCP, UDP, NNG, MoQ, then WebRTC in the add-on. Each PR deletes that transport's queue, demux, sink and option-parsing copies (TRB-3, TRB-38, TRF-32, SHR-35, TRB-26, SHR-9) and removes its Sender/Receiver Build.cs dependency.
5. **Typed config and consumer API (SHR-36, TRB-27, SHR-16, TRF-38).** Option schemas per transport, `FO3DTransportOptionsView`, removal of the LiveKit fields, `SubmitFrame` view and owned forms, deletion of `Send(SubjectList)`.
6. **Following release:** delete the shims and bump `O3D_TRANSPORT_API_VERSION`.

Docs (WP-D3): the threading tables above go into `docs/transports.md`.

## Verification / acceptance

- The 0006 conformance suite passes for every transport after each PR, plus new cases: `Start` without consumer fails with `NoConsumer`; `Stop` while four threads call `SendSerialized` and a fake audio thread submits PCM is clean under ASan (WP-S5 stress, 1,000 cycles); an unregister during a live session stops and releases the instance and logs no leak.
- An add-on built with a different `O3D_TRANSPORT_API_VERSION` logs the mismatch and registers nothing (WP-F11 acceptance).
- `grep -rn "TQueue<.*Mpsc>" Plugin/Source/Open3DTransport*` finds nothing outside tests; no transport Build.cs names Open3DSender or Open3DReceiver.
- No raw pointer or reference to a sender, receiver or UObject is reachable from a sink or worker (review checklist §7 item 2).
- Net lines under `Plugin/Source/Open3DTransport*` go down (WP-A1 acceptance).

## Open questions for the maintainer

1. **needs-verification:** UE 5.7 spellings of `TValueOrError`, `UE_DEPRECATED` and `FRWLock` read/write scope helpers. Default: plain result struct (E1), which needs none of them.
2. **needs-verification:** at editor exit, hot reload and Live Coding, are plugin modules shut down before or after worlds and components are destroyed? Default: drain in `ShutdownModule` regardless, and never free an FFI DLL with live instances.
3. **needs-verification:** does `ISocketSubsystem::GetAddressInfoAsync` exist in 5.7 with a callback usable from a worker thread? Default: call the synchronous `GetAddressInfo` on the transport worker, which is off the game thread either way.
4. Keep global singletons (module-owned) instead of an injected `FO3DRuntimeContext` for v1? **Default: yes**, revisit only if per-PIE isolation is requested.
5. Forwarding shims for exactly one release? **Default: yes**, removed in the next minor release with an API version bump.
6. Consumers called on the Poll thread (game thread today) rather than on a transport worker? **Default: Poll thread**, as above.

## Addendum: sink and FFI lifetime (WP-S5)

- **Status:** Accepted with WP-S5 (2026-09-29). Minimal per-transport fix now; WP-A1 folds the pieces into item 7 above.
- **Findings:** TRF-1, TRF-10, TRF-12, TRF-40, TRB-10, TRB-11, TRB-12, TRB-30, TRB-35, RCV-1, SND-6, SND-7, SHR-10, SHR-15.

**Chosen guard: a ref-counted publish state, not `TO3DSinkOwnerGuard<T>`.** The Sockets `OwnerGuard` keeps a raw `Owner*` and holds its lock across the owner's own code, which is the TRB-10 contention. A template that wraps `T*` would copy both properties. Instead each sender owns a `TSharedPtr<F<Transport>AudioState, ESPMode::ThreadSafe>` created in its constructor and never reassigned. The state holds only what the audio path needs (a lifetime gate, the hand-off queue and wake event, FFI handles where the FFI needs them, a last-subject slot) and **never** a pointer or reference to the sender, a receiver, a UObject or a socket. Each sink holds a **strong** reference to the state, the gate epoch it was created in, and its own encoders. A strong reference is used rather than a `TWeakPtr` because the state's destructor does no FFI, socket or UObject work, so any thread may safely drop the last reference, and a weak pin per audio buffer would add cost without changing who can end up last owner.

**Lifetime gate (`FO3DLifetimeGate`, Open3DShared).** An `FRWLock` plus an atomic open epoch (0 means closed). A producer enters with `FO3DLifetimeGate::FReadScope(Gate, Epoch)`, which fails fast when the gate is closed or the epoch has moved on, and otherwise holds the read lock for one encode and hand-off. The read lock is never held across a socket or FFI send, except for the WebRTC audio publish below, and is never nested.

**`Stop()` ordering.** (1) `Gate.Close()`: clears the epoch, then takes and releases the write lock, so it returns only after every in-flight submit has left, and later submits fail fast. The wait is bounded by one encode (or one `lk_audio_track_publish_pcm_i16`). (2) Stop and join the transport worker. (3) Destroy FFI handles and sockets. (4) Drain queues. `Start()` and `Initialize()` open a new epoch. A sink is bound to the epoch it was created in, so a sink from an earlier session stays dead after a restart and never publishes into the next one.

**Hand-off off the audio thread (TRB-10).** Sinks encode into sink-local scratch and push bytes into an MPSC queue owned by the state (`FO3DEncodedPayloadQueue`: `TQueue<..., EQueueMode::Mpsc>` with `fetch_add`/`fetch_sub` byte accounting and a cap). The transport worker drains it and is the only thread that touches the socket for audio. TCP and NNG share one queue for mocap and audio; UDP gains a small audio worker; MoQ drains an audio queue beside its mocap queue. The wake event is an `FEventRef` owned by the state, so no thread can trigger an event that `Stop()` has returned to the pool (TRB-12). The audio thread never takes a socket lock.

**One encoder per sink and stream label (TRB-11, TRF-10, TRF-40).** `FO3DSinkAudioEncoder` (Open3DShared) keeps a small map from stream label to `O3DAudio::FFrameEncoder`, built from an immutable config snapshot taken on the game thread when the sink is created. Nothing reconfigures a live encoder; a new config means a new sink. A sink-local lock (never shared with the game thread or the network worker) serialises concurrent submits to one sink.

**One decoder per stream (SHR-15).** `O3DAudio::FMultiStreamFrameDecoder` keys `FFrameDecoder`s by `(SourceGuid, StreamLabel)` with an LRU cap and replaces the single decoder in every receiver. It has the same `Decode` signature.

**FFI callbacks (TRF-12).** `user_data` is an opaque token from `TO3DFfiContextRegistry<T>` (Open3DShared, header-only), never an object address. The thunk resolves the token to a `TWeakPtr` under a read lock. Unregistered or late tokens resolve to nothing. The resolved context holds only atomics and weak references, so an FFI thread that ends up holding the last strong reference destroys nothing but plain data. MoQ connection and subscriber callbacks, the NNG pipe callback and the WebRTC sender connection callback use it. **Exception:** the WebRTC receiver keeps `this` as `user_data`, relying on the LiveKit contract that no callback runs after `lk_disconnect`/`lk_client_destroy` returns (`livekit_ffi.h:408-409`), which its `Stop()` (also run by the destructor) calls. It now reads its audio sink under a dedicated lock that `Stop()` does not hold while calling into LiveKit.

**Who may hold the last strong reference.** Sender, receiver, receiver source and FFI handle owners: the game thread only. Publish states, sinks, contexts and the receiver-side audio sink: any thread, because their destructors free only memory and pooled events.

**Receiver audio sink (RCV-1).** The source builds an immutable `FO3DReceiverAudioMetaDefaults` snapshot (source GUID, stream id, default rate and channels) when it starts the transport and gives it to the sink. The sink has no back-reference to the source and marshals PCM to the game thread by value.

**Sender capture (SND-6, SND-7).** The capture component publishes an immutable `FO3DSenderAudioCaptureParams` snapshot (sink, label, gain, target rate and channels) into a small router object on the game thread, swapped under a lock held only for the pointer copy. The submix listener and the mic callback hold the router, never the UObject, and each has its own scratch buffer. The listener remembers the submix it was registered on and is always unregistered from that one; registration is idempotent.

**Audio bus threading (SHR-10).** `FO3DAudioBus` stays a plain multicast delegate and is game-thread-only: `OnPcm16()` and `PublishPcm16()` `check(IsInGameThread())`, and publishing with no listener returns early.

**Absorbed by WP-A1:** `FO3DLifetimeGate`, `FO3DEncodedPayloadQueue`, `FO3DSinkAudioEncoder` and the per-transport audio states become `FO3DAudioPublishState` and `FO3DSendQueue`/`FO3DTransportWorker` of item 7; the per-transport sink classes collapse into `FO3DSenderAudioSinkBase`; `FMultiStreamFrameDecoder` moves into `FO3DUnifiedReceiveDemux`; `TO3DFfiContextRegistry` backs the `FLkFfiApi`/`FMoQFfiApi` tables (ADR 0006 F2), and the WebRTC receiver exception is removed there.

## Addendum: implementation notes (WP-A1 PR 2, 2026-10-01)

- **Live lists.** Each registry entry owns a live list of weak references to the senders and receivers `CreateSender`/`CreateReceiver` handed out. A legacy entry keeps its list across deprecated edits. `GetNumLiveInstances(FName)` counts what is still referenced, and keeps counting instances that leaked from an earlier registration of the name, so registering the name again cannot hide them from `FO3DFfiLibrary`.
- **Drain order.** Unregistering (resetting the handle, or the deprecated unregister call that empties a legacy entry) runs on the game thread:
  1. The name leaves the map and its live list is closed, so a factory still running for it has its new instance stopped and gets null back.
  2. `OnTransportUnregistering(FName)` is broadcast (the name item 5 uses).
  3. The registry stops what is still alive and, for a receiver, also clears its consumer and control sink (receivers already release the control sink in `Stop`, ADR 0011).
  4. Anything still referenced is logged as one Error with the transport name, its owning module and the sender and receiver counts. Per-instance owners are not recorded; the module is the owner the registry knows.

  `OnTransportsChanged` fires last.
- **Who subscribes.** `FO3DSenderTransportController` subscribes while it holds a sender. On the notification it first calls a handler the sender component installs, which tears down the audio capture's sink and the control publisher (`TeardownTransport`), then stops and releases the sender. `FO3DReceiverSource` subscribes while it holds a receiver and runs `StopTransport`, which now also clears the receiver's control sink after `Stop`. Both unsubscribe on every path that drops the instance.

Module order: reset the registration, then (MoQ) shut down the callback dispatcher, then `Unload()`.
- **Game-thread checks.** `Register`, unregister and `EditLegacyDescriptor` now `check(IsInGameThread())`, as item 4 says. `CreateSender`/`CreateReceiver` stay callable on any thread (the PR 1 contract); the closed-list rule makes a create that races an unregister safe without a check.

- **Verification.** `Open3DBroadcast.Shared.TransportLifetime.*` covers the Verification case "an unregister during a live session stops and releases the instance and logs no leak", both with test owners on a private registry and with the real sender component and receiver source over a fake transport. ## Addendum: implementation notes (WP-A1 PR 4a, 2026-10-02)

- **Status:** step 4 of the Implementation outline has started. The building blocks of item 7 are in Open3DShared and Loopback runs on them. TCP, UDP, NNG, MoQ and the WebRTC add-on still use their own copies and migrate one per PR, in that order (next: TCP). Steps 5 and 6 are not started. Nothing here changes the Decision; it records choices item 7 left open and where the code differs from it.
- **`FO3DSendQueue` (`Transport/O3DSendQueue.h`).** One `TQueue<FO3DSendItem, EQueueMode::Mpsc>` with item kinds `Mocap`, `Audio`, `Control`. Each kind has its own `MaxItems`/`MaxBytes` and its own atomic counters (pending items and bytes, enqueued, refused, dropped, dequeued). A producer reserves with `fetch_add` and rolls back with `fetch_sub` when it crossed a limit, so the queue never holds more than a limit (TRB-3); near a limit two racing producers may both be refused once.
  - **Per-kind limits instead of one shared cap.** Item 7 says audio and control are never dropped for mocap. With one shared byte cap, a mocap flood would still refuse audio and control at the hard cap, so each kind is accounted and limited on its own. This is also what ADR 0011 asks of Loopback ("three queues stay independent").
  - **Mocap policy is a setting.** `EO3DMocapOverflow::DropOldest` is item 7's rule: the limits are soft caps, producers are refused at twice the cap, and `Dequeue` discards the oldest mocap items while the backlog is over the soft cap. `RefuseNewest` makes the limits hard caps and discards nothing queued; Loopback uses it, because it reports `ReliableOrdered` (ADR 0005) and always refused the newest frame. Each later migration picks the policy that matches its delivery guarantee and states it.
  - **Control** has a default cap of 1,024 items (Loopback's old control queue), is never evicted and never expires. **Audio** is refused at its cap and never evicted. The optional age limit (TRB-14) applies to mocap and audio at `Dequeue`; control's staleness is handled by its own TTL and snapshots (ADR 0011).
  - The consumer is the transport worker, or for Loopback the receiver's `Poll`. Items keep their order across kinds, so control is in-band with the frames around it.
- **`FO3DTransportWorker` and `FO3DReconnectPolicy` (`Transport/O3DTransportWorker.h`).** The worker is an `FRunnable` that runs a body returning its next wait in ms; it waits on the send queue's event (so every `Enqueue` wakes it) or its own, and `Stop()` wakes and joins it. The body owns the socket or FFI handle and runs connect, reconnect and FFI lifecycle calls. The policy is exponential backoff with jitter (seeded `FRandomStream`, deterministic in tests), reset on success, and an optional attempt limit. Loopback needs neither (no I/O); TCP, UDP, NNG and MoQ adopt them as they migrate, and UDP and WebRTC move their sends onto the worker then (TRB-20, ADR 0008 item 8).
- **`FO3DUnifiedReceiveDemux` (`Transport/O3DUnifiedReceiveDemux.h`).** `ProcessMessage` classifies a buffer once by the envelope header; `DeliverMocap`, `DeliverAudioPayload` (with or without a known codec), `DeliverAudioFrame` and `DeliverControlEnvelope` serve transports whose channel already says what a buffer is (Loopback items, MoQ tracks, WebRTC labels). Control goes through `O3DS::TryGetControlPayload`, the CTL-2 classifier; a malformed control envelope is dropped, never passed as mocap. Choices item 7 left open:
  - A buffer that starts with the envelope magic but whose header does not fit is `Malformed`. The per-transport copies passed it on as legacy raw mocap.
  - Raw (non-enveloped) bytes are still mocap by default (`bAcceptRawMocap`), as on TCP, UDP and NNG today.
  - The demux holds the consumer, the audio sink and the control sink strongly and drops them in `ReleaseSinks()`, which a receiver calls from `Stop()` (item 3, TRF-38). It owns the per-stream decoder map (`O3DAudio::FMultiStreamFrameDecoder`, SHR-15) and a reused mocap buffer; until step 5's view form of `SubmitFrame`, enveloped mocap is still copied once into that buffer, without a per-frame allocation once it has grown.
  - It is single-threaded: the thread that calls `Poll()`.
- **Audio sinks (`Transport/O3DSenderAudioSinkBase.h`).** `FO3DSenderAudioSinkBase` and the WP-S5 `FO3DGatedSenderAudioSink` moved here from Open3DSender unchanged (forwarding header kept for one release), so unmigrated transports keep compiling. New: `FO3DAudioPublishState` (lifetime gate, a reference to the transport's `FO3DSendQueue`, last-subject slot, audio byte counter; no sender, socket or FFI handle) and `FO3DQueuedSenderAudioSink`, which encodes under the gate's read lock with its own encoders and enqueues audio items; the bytes are a unified audio envelope or the bare payload (`EO3DAudioWireFormat`, the latter for MoQ). Item 7's `bOpen` flag and `FRWLock` are the existing `FO3DLifetimeGate`. A migrated sender creates one state per `Initialize` and closes it in `Stop()`. `FO3DGatedSenderAudioSink` is deleted when the last transport has migrated. The receiver-side `FO3DReceiverAudioSinkBase` of item 7 (RCV-1) belongs to the receiver source, not to a transport, and is not part of this PR.
- **`O3DTransportOptions` (`Transport/O3DTransportOptions.h`).** Strict getters over the option map (`GetInt`, `GetDouble`, `GetBool`, `GetString`) and `ParseHostPort`: optional `scheme://`, path and query ignored, bracketed IPv6 (with a zone), bare IPv6 only without a port, ports 1 to 65535 in digits only, an optional default port, user info refused. `ResolveHostPort` uses `ISocketSubsystem::GetAddressInfo` synchronously, which open question 3's default allows on a transport worker; `GetAddressInfoAsync` stays unverified. `O3DHelpers::NormalizeTcpUrlHostPort` is deleted (SHR-9). Until step 5's `FO3DTransportOptionsView`, the getters take `FO3DTransportConfig::AdvancedParams`, which the sender component and the receiver source fill from their options before the configure function runs; that is what lets a transport drop its Open3DSender and Open3DReceiver dependency now.
- **Shared audio (de)serializers (SHR-35).** `O3DAudioSerialization.cpp` already had one header writer and one reader for both payload layouts (`SerializeAudioImpl`, `DeserializeAudioImpl`). This PR adds `O3DAudio::TryGetAudioPayloadCodec`, the header peek MoQ keeps privately today (`TryGetAudioCodecFromFrame`), so the demux can parse a bare payload. Merging the three frame structs (`FPcm16Frame`, `FEncodedAudioFrame`, `FEncodedFrame`) is left to the migration that touches their users.
- **Loopback.** The channel is one `FO3DSendQueue` per name (`RefuseNewest`; `loopback.maxqueue`, `loopback.maxaudioqueue`; control default cap). Its own packet structs, three queues, counters, audio sink class, demux code and option loops are gone; the configure functions read the config, and the Build.cs names neither Open3DSender nor Open3DReceiver. Behaviour changes: kinds now leave the channel in send order (control was delivered first in each `Poll`), audio crosses the channel as a unified envelope (metadata is range-checked on the way, SHR-8), and the sender reports `PendingBytes`. `grep -rn "TQueue<.*Mpsc>" Plugin/Source/Open3DTransportLoopback` finds nothing. Net lines under `Source/Open3DTransport*`: 1,028 to 717 (-311).
- **Interface version stays 4.** Only standalone types were added; the two moved classes keep their layout and are not used by the add-on. No type the version covers changed layout, vtable or threading rule.
- **Verification.** `Open3DBroadcast.Shared.SendQueue.*`, `.TransportWorker.*`, `.ReconnectPolicy.*`, `.ReceiveDemux.*`, `.AudioSinkBase.*`, `.HostPort.*` and `.TransportOptions.TypedGetters` cover the blocks, including four producers against a live consumer and 1,000 close cycles of the publish state under a fake audio thread. For Loopback the conformance suite (with the control and step-3 cases) and the existing Loopback tests run unchanged; `Open3DBroadcast.Transport.Loopback.Lifetime.StopWhileSending` is the Verification case "Stop while four threads call SendSerialized and a fake audio thread submits PCM" (1,000 cycles; ASan where available). The same case for the other transports comes with their migrations.

## Addendum: implementation notes (WP-A1 PR 4b, 2026-10-02)

- **Status:** TCP runs on the item 7 building blocks. UDP, NNG, MoQ and the WebRTC add-on are still to migrate, in that order (next: UDP, PR 4c). Nothing here changes the Decision; it records how TCP maps onto it and where behaviour changed.
- **Sender.**
  - One `FO3DSendQueue` holds frames, audio and control.
  - The mocap policy is `RefuseNewest`: TCP reports `ReliableOrdered` (ADR 0005) and always refused the newest frame, so `DropOldest` would have silently discarded frames a reliable transport accepted.
  - `tcp.maxqueue` is the byte limit of frames and, separately, of audio. Control keeps the queue's default cap. Before, all three shared one byte cap, so a full frame queue refused control and audio. That is the "never dropped for mocap" case item 7 and ADR 0011 rule out.
  - `tcp.maxqueueage` is the queue's age limit, so control no longer expires there.
  - Items hold the bare payload. The worker writes the core's frame header and then the payload from the item (two sends, one frame), so the producer no longer copies the payload into a framed buffer. The half-frame rule of TRB-2 is unchanged.
  - The worker is an `FO3DTransportWorker` whose body is one iteration of the old loop.
  - The sink is `FO3DQueuedSenderAudioSink`. The old sink refused PCM while no receiver was connected. To keep that, `FO3DAudioPublishState` gained a peer flag (`SetPeerReady`/`IsPeerReady`, default true) that the sink checks inside the gate; the TCP worker sets it on accept and clears it on drop. It doubles as the sender's "has client" flag.
  - The listen socket stays on the game thread in `Start`, which must report `AddressInUse` at once (item 3). So the bind host must be an IP literal or a wildcard and `ResolveHostPort` resolves no name there; a host name never worked as a bind address before either (`SetIp`).
- **Receiver.** Item 7 puts connect, reconnect and name resolution on the worker. Doing only those there would leave two threads on one socket, so the worker owns the socket entirely.
  - The worker resolves (`ResolveHostPort`, synchronous `GetAddressInfo`, open question 3's default) and connects with a socket of the resolved protocol family, so IPv6 works.
  - It reconnects with `FO3DReconnectPolicy` (`tcp.backoff`/`tcp.maxbackoff`, ×2, ±20% jitter). As before, the backoff resets only once a connection carries data.
  - It reads, frames with `O3DS::TcpStreamParser`, drops keepalives (they only refresh the idle timer) and hands payloads to a bounded hand-off queue.
  - The hand-off reuses `FO3DSendQueue` (one kind, `RefuseNewest`, 8 MiB or one `tcp.maxframe`, whichever is larger) rather than adding a receive-queue type. When it is full the worker keeps the refused payload, stops reading and refreshes its idle timer, so the kernel buffers fill and TCP flow control slows the sender (the SlowReader test depends on this).
  - `Poll` (game thread, at most 256 payloads or 8 MiB) is the only place the demux, and so the consumer, the audio sink and the control sink, are called (item 3, open question 6).
  - Connection state after `Start` changes on the worker: state first, then the `IsConnected`/`ConnectCount` flags, so tests that wait on a flag see the matching state.
  - `Stop` joins the worker. That is bounded by its 10 ms socket waits, except while a host name is being resolved, which can take as long as the platform's DNS timeout. This is the cost of the synchronous resolver; an async one (open question 3) would remove it.
- **Options.** `ParseTcpEndpoint` keeps the old precedence (a `tcp://` URI, then `host` and `port`, then `StreamId`), with `ParseHostPort`'s strict rules. The configure functions read `Config.AdvancedParams`, as Loopback's do; the TCP files include neither Open3DSender nor Open3DReceiver headers. `Open3DTransportSockets.Build.cs` keeps both dependencies only for UDP's configure functions, which PR 4c rewrites.
- **Removed:** the TCP publish state with its `FO3DEncodedPayloadQueue`, the TCP sink class, the enqueue-time framing, the receiver's demux branches and its own backoff arithmetic, `SocketsTcpAudio.*` and `O3DSockets::BuildTcpUri`. Net lines under `Source/Open3DTransport*`: -195.
- **Interface version stays 4.** The add-on uses none of the changed types; `FO3DAudioPublishState` gained two inline members and an atomic, and it was introduced in PR 4a with no add-on user.
- **Verification.** The TCP conformance profile and the existing TCP tests (burst, slow reader, reconnect after sender restart, idle keepalive, audio round trip, audio refused without a client, the WP-S5 start/stop stress, results) are unchanged.
  - `Open3DBroadcast.Transport.Sockets.Tcp.AudioIndependentOfFrameQueue` fills the frame budget behind a receiver that does not poll, then checks that audio and control are still accepted and that everything accepted arrives.
  - `.ReceiverBacksOffWithoutSender` checks that the worker retries with backoff and connects without `Poll`, and that data resets the backoff.
  - `.StopWhileSending` is the Verification Stop-under-load case: 1,000 cycles, 50 of them with a connected client that does not read.

## Addendum: implementation notes (WP-A1 PR 4c, 2026-10-02)

- **Status:** UDP runs on the item 7 building blocks. NNG, MoQ and the WebRTC add-on are still to migrate, in that order (next: NNG, PR 4d). Nothing here changes the Decision; it records how UDP maps onto it and where behaviour changed.
- **Sender.**
  - One `FO3DSendQueue` holds frames, audio and control, and an `FO3DTransportWorker` sends every item. Before, `SendSerialized` called `SendTo` (and fragmented) on the caller's thread under a lock (TRB-20).
  - The mocap policy is `DropOldest`, soft cap 4 frames or 16 MiB, so callers are refused only at 8 frames or 32 MiB. UDP reports `Unreliable` (ADR 0005), it never retransmitted, and a frame that is late is worth less than the next one (ADR 0008 decision driver 4). That is the item 7 default for an unreliable transport. `RefuseNewest` would send stale frames first after a stall. The old sender had no queue; the cap keeps the added latency to a few frames.
  - Audio has its own 1 MiB byte budget (the WP-S5 sink's). Control keeps the queue's cap of 1,024. Neither is dropped for frames. No age limit: the drop policy already bounds the backlog.
  - Results: `SendSerialized` reports `Queued`, not the socket's result. A failed `SendTo` (including a full send buffer, `SE_EWOULDBLOCK`) is counted in `DroppedFrames` and `SendErrors` after the fact. `FramesSent`/`BytesSent` count datagrams actually sent. `DroppedFrames` adds the frames the queue evicted, but not those a `Stop` or `Start` empties.
  - Destination: an IP literal is resolved in `Initialize` with `ResolveHostPort`, which does no DNS for a literal, so a bad literal is still `InvalidConfig` there. A host name is resolved on the worker with `ResolveHostPort` and retried with `FO3DReconnectPolicy` (default settings) until it resolves; the state is `Connecting` until then and becomes `Connected` from the worker (item 3 allows worker-thread changes after `Start`). This is the only "reconnect" concept UDP has; a connectionless socket has no connection to lose. Before, `Initialize` used `SetIp` and a host name failed with `InvalidConfig`. The socket's protocol follows the resolved address, so IPv6 works.
  - The sink is `FO3DQueuedSenderAudioSink`. The old sink refused PCM until the socket existed; the publish state's peer flag (PR 4b) now means "the socket exists", set by the worker or `Start` and cleared before the socket is destroyed.
  - `Stop` keeps the WP-S5 order: close the publish state (waits for in-flight submits), join the worker, destroy the socket, empty the queue.
- **Receiver.** Receive threading stays on `Poll` ("Not decided here"). Each complete message goes to `FO3DUnifiedReceiveDemux::ProcessMessage` instead of the receiver's own branches and audio decoder. Consequences: the consumer is held strongly and released in `Stop` (TRF-38), as for TCP; a damaged envelope is dropped; rejected audio, malformed and oversize messages count in `ReceiveErrors`. The bind address keeps its rules ("" and `*` bind every interface, `localhost` is 127.0.0.1) and must otherwise be an IP literal, checked with the new `O3DTransportOptions::IsIpLiteral`; IPv6 literals now bind an IPv6 socket.
- **Windows.** An ICMP port-unreachable makes the next `recv` on that UDP socket fail with `WSAECONNRESET`. The sender never calls `recv`, so moving it to a worker changes nothing there. The receiver's handling is unchanged: an error other than "would block" ends that `Poll`, and the next `Poll` reads again.
- **Options.** `O3DSockets::ParseEndpoint` keeps the old precedence (a `<scheme>://` URI, then `host` and `port`, then `StreamId`) with `ParseHostPort`'s strict rules; TCP uses it too, replacing `ParseTcpEndpoint`. `udp.*` values use the strict getters. `ConfigureUdpSender`/`ConfigureUdpReceiver` read `Config.AdvancedParams`, so `Open3DTransportSockets.Build.cs` no longer names Open3DSender or Open3DReceiver, and no file in the module includes their headers (step 4's "drops its Build.cs dependency").
- **Removed:** the UDP sender's send lock and synchronous send path, the UDP audio sink and publish state, the receiver's demux branches and audio decoder, `SocketsTransportConfigCommon.cpp` (`ParsePositiveInt`, `ParseBoolOption`), the remaining `O3DSockets` option parsers and `BuildUdpUri`. Net lines under `Open3DTransportSockets`: -441.
- **Interface version stays 4.** `O3DTransportOptions::IsIpLiteral` is a new free function; the add-on uses none of the changed types.
- **Verification.** The UDP conformance profile and the existing UDP and sockets tests (control datagrams, control never fragmented, the WP-S5 start/stop stress with audio, results, capabilities) are unchanged.
  - `Open3DBroadcast.Transport.Sockets.Udp.QueueDropsOldestUnderBackpressure` pauses the worker (test hook), sends 20 frames, checks that 8 are accepted and 12 refused, then that exactly the 4 newest accepted frames arrive and the stats add up.
  - `.AudioIndependentOfFrameQueue` fills the frame queue behind a paused worker, then checks that audio and control are still accepted and arrive.
  - `.StopWhileSending` is the Verification Stop-under-load case: 1,000 cycles with four send threads and an audio thread, to a bound socket that discards the datagrams.

## Addendum: implementation notes (WP-A1 PR 4d, 2026-10-02)

- **Status:** NNG runs on the item 7 building blocks. MoQ and the WebRTC add-on are still to migrate (next: MoQ, PR 4e). Nothing here changes the Decision; it records how NNG maps onto it and where behaviour changed.
- **Sender.**
  - One `FO3DSendQueue` holds frames, audio and control; an `FO3DTransportWorker` replaces the hand-written runnable and hands each item to `nng_send` with `NNG_FLAG_NONBLOCK`.
  - The mocap policy is `RefuseNewest` with `nng.qmax` as the byte limit, for every mode. That is what the sender did before (its `FO3DEncodedPayloadQueue` refused the newest payload), and it fits every mode. The worker never holds a backlog: `NNG_FLAG_NONBLOCK` returns `NNG_EAGAIN` when no peer is ready or NNG's own send buffer (1,024 messages) is full, and the worker then drops that item, which is the oldest queued. So "drop the oldest" already happens at the worker for a slow or absent peer, pub/sub stays lossy, and pair and push/pull keep everything NNG accepted in order. The application queue only fills when the worker itself falls behind. There, `DropOldest` would add a second, silent discard to modes that report `ReliableOrdered`, and would double the limit `nng.qmax` names; the existing `Queue.Limit` and conformance backpressure tests pin the refusal.
  - `nng.qmax` (clamped to 64 KiB to 512 MiB, as before) is the byte limit of frames and, separately, of audio. Control keeps the queue's cap of 1,024. Before, all three shared one cap, the case item 7 and ADR 0011 rule out.
  - `FramesSent` is counted on the worker once `nng_send` took the message, as before (#301's conformance wait depends on it), but for frames only; audio adds to `BytesSent`. `DroppedFrames` counts refused frames, frames dropped at the worker and failed frame sends. `SendErrors` counts failed sends other than `NNG_EAGAIN`.
  - The sink is `FO3DQueuedSenderAudioSink`. The publish state's peer flag stays true: the old sink queued audio without a peer and NNG drops it then, so nothing changes.
  - **Reconnect.** NNG redials a dropped connection itself (`NNG_OPT_RECONNMINT`/`RECONNMAXT`, NNG's defaults; the transport never set them). The worker's `FO3DReconnectPolicy` (0.1 s doubling to 5 s, ±20% jitter; the old arithmetic without jitter) only paces reopening a socket that does not exist: an open, listen or dial that failed, or a socket NNG reported `NNG_ECLOSED`. While a socket exists the policy is idle, so the two loops never run against each other. Replacing NNG's redial with the policy would mean closing and reopening sockets the library already manages, losing pipe state for no gain.
  - `Start` still opens the socket on the game thread, because a listener must report `AddressInUse` at once (item 3); a dial is non-blocking.
  - `Stop` keeps the WP-S5 order: close the publish state (waits for in-flight submits), join the worker so no `nng_send` is in flight, `nng_close` the socket, empty the queue. Pipe callbacks still reach only the token-resolved pipe context.
- **Receiver.** Receive threading stays on `Poll`, as for UDP: NNG's own I/O threads already receive into the socket's receive buffer (1,024 messages for sub), so a transport worker would only add a second queue. Each message goes to `FO3DUnifiedReceiveDemux::ProcessMessage` (stream id `Options.StreamId`, limit 50 MiB like `NNG_OPT_RECVMAXSZ`). Consequences: the consumer is held strongly and released in `Stop` (TRF-38); a damaged envelope is dropped; `FramesReceived`/`BytesReceived` count mocap only; rejects and receive errors count in `ReceiveErrors`; a control envelope is no longer counted in `DroppedFrames`. Reopening a missing socket uses the same `FO3DReconnectPolicy` settings; a listener used to retry on every `Poll`.
- **Options.** NNG's own Uri shape stays (`nng+<mode>://host:port/topic?role=&topic=&host=&port=&mode=`), but every host and port inside it, and the `host`, `port` and `nng.qmax` options, go through `O3DTransportOptions` (`ParseHostPort`, `TryParsePort`, `TryParseInt`, `GetString`). A malformed one is `InvalidConfig` with a message instead of being read as far as it parses. A StreamId that is not an endpoint is a label and is still ignored. The configure functions read `Config.AdvancedParams`, so `Open3DTransportNNG.Build.cs` no longer names Open3DSender or Open3DReceiver, and no file in the module includes their headers.
- **Removed:** `FNngSenderPublishState`, `FNngSenderAudioSink`, `FNngSenderRunnable` and the sender's mutexes, the receiver's demux branches and audio decoder, and the module's `ParseInt`, `ParseUInt64`, host:port and bracket helpers. Net lines under `Open3DTransportNNG`: -349.
- **Interface version stays 4.** No public type changed; `O3DNngTesting::SenderSetWorkerPaused` is a test-only export.
- **Verification.** The NNG conformance profile and the existing NNG tests (round trip, queue limit, demux, mode and role pairs, option parsing, the WP-S5 start/stop stress, results, capabilities, control in every mode) are unchanged.
  - `Open3DBroadcast.Transport.NNG.QueueRefusesNewestUnderBackpressure` pauses the worker (test hook; the hook returns once the worker has seen the flag), sends 20 frames of 8 KiB into a 64 KiB queue, checks that the first 8 are accepted and the rest refused, then that exactly those 8 arrive in order over pair.
  - `.AudioIndependentOfFrameQueue` fills the frame budget behind a paused worker, then checks that audio and control are still accepted and arrive.
  - `.StopWhileSending` is the Verification Stop-under-load case: 1,000 cycles with four send threads and an audio thread. Push senders dial a pull receiver that listens for the whole test, so no listener is reopened on one port; every 50th cycle waits until the sender is connected and has sent.

## Addendum: implementation notes (WP-A1 PR 4e, 2026-10-02)

- **Status:** MoQ runs on the item 7 building blocks. Only the WebRTC add-on is still to migrate (next: PR 4f). Nothing here changes the Decision; it records how MoQ maps onto it and where behaviour changed.
- **Where moq-ffi calls back.** Connection-state and subscriber-data callbacks arrive on moq-ffi's threads; the session wrapper's thunks resolve an opaque token and hand the work to `FMoQAsyncDispatcher`, which runs it on the game thread. Blocking calls (`moq_connect`) run on a background task. So the receiver's demux runs on the game thread, in `Poll`, as item 3 and open question 6 require; the data callback only puts the payload on a hand-off queue.
- **Sender.**
  - One `FO3DSendQueue` holds frames, audio and control; an `FO3DTransportWorker` replaces the hand-written runnable and the separate audio queue, and publishes each item on its track's publisher (a snapshot taken under the publisher lock, TRF-9).
  - The mocap policy is `RefuseNewest` with `queue_bytes` (clamped to 256 KiB to 256 MiB) as the byte limit. That is what the sender did before, and it is the right policy here for the same reason as NNG: the worker never holds a backlog. An item whose publisher is not ready (not connected, the track not yet announced) is dropped by the worker, oldest first, so a reconnect never replays stale frames; the queue only fills when the worker falls behind the relay. Delivery is `Unreliable` (ADR 0005 Q5), but `DropOldest` would also change what `queue_bytes` means (twice the limit admitted), which `Sender.BackpressureByteLimit` and the conformance backpressure case pin.
  - Audio keeps its own 1 MiB budget. Control, which used to share `queue_bytes` with the frames, has the queue's cap of 1,024: the "never refused for mocap" rule of item 7 and ADR 0011. `SendControl` is still refused with `NotConnected` until the control track is announced.
  - The sink is `FO3DQueuedSenderAudioSink` with `EO3DAudioWireFormat::AudioPayload`, the bytes MoQ's sink produced (`O3DAudio::SerializeForTransport`). The peer flag stays true: the old sink queued audio while disconnected and the worker dropped it, which is unchanged.
  - Counting: `FramesSent` for published frames only (audio adds to `BytesSent`); `DroppedFrames` for refused frames, frames dropped at the worker, failed frame publishes and frames still queued at `Stop`; `SendErrors` for failed publishes of any kind.
  - `Stop` keeps the WP-S5 order: close the publish state, join the worker, empty the queue, release the publishers, disconnect.
- **Reconnect.** moq-ffi has no reconnect of its own: every attempt is a fresh client that ends in `CONNECTED` or `FAILED`. The transport's loop (game thread, `Tick` and `Poll`, the session callbacks) stays as it is, with `MoQHelpers::ComputeBackoffDelaySeconds` and the connect timeout. `FO3DReconnectPolicy` is not used: its jitter is symmetric (±20%), while MoQ's removes up to 25% and never adds, and `Sender.ReconnectReannounces`, `Sender.ConnectTimeoutRetriesWithBackoff`, `Receiver.SubscribeRetryBackoff` and `Backoff.CappedJitter` pin those exact delays on a manual clock. There is one loop, so nothing runs against anything. Converging the two schedules is left to a later change that may edit those tests.
- **Receiver.** The hand-off from the data callback to `Poll` is an `FO3DSendQueue` (game thread on both sides; mocap and audio 16 MiB each, control 1,024, `RefuseNewest`) instead of a locked `TQueue` with one shared 16 MiB. `Poll` routes each payload through `FO3DUnifiedReceiveDemux`: `DeliverMocap` (the mocap track carries bare frames, never envelopes), `DeliverAudioPayload` (codec from the payload header, TRF-37, now `O3DAudio::TryGetAudioPayloadCodec`), `DeliverControlEnvelope`. Consequences: the consumer is held strongly and released in `Stop` (TRF-38), as for the other transports; `FramesReceived`/`BytesReceived` count mocap only; rejects count in `ReceiveErrors`.
- **Options.** `O3DTransportOptions::GetString` reads every key; `queue_bytes` uses `TryParseInt` and `connect_timeout` `TryParseDouble`. The defaults for a malformed value are unchanged.
- **Module dependencies.** Open3DReceiver is gone from `Open3DTransportMoQ.Build.cs`; `ConfigureReceiver` never read its settings. Open3DSender stays, for `UO3DSenderComponent::SubjectName` only: `ConfigureSender` uses it as the default stream id (and so the default track name), and `FO3DTransportConfig` has no field for it. Putting it in `StreamId` from the component would change NNG, whose parser reads a host, port and topic from the stream id. ADR 0007 step 5 (typed config) is where it moves; the relay URL is now read from `Config.AdvancedParams`.
- **Removed:** `FO3DMoQSenderAudioSink`, `FMoQSenderAudioState`, `FSendWorker`, the sender's queue, mutexes and payload struct, the receiver's payload struct, queue mutex, demux branches and audio decoder, and `MoQHelpers::GetAdvancedOption`, `ParseUInt64` and `TryGetAudioCodecFromFrame`. Net lines under `Open3DTransportMoQ`: -386.
- **Interface version stays 4.** No public type the add-on uses changed; `MoQTesting::SenderSetWorkerPaused` is a test-only export.
- **Verification.** The MoQ conformance profile, the existing MoQ tests (fake moq-ffi) and the network-gated relay tests are unchanged.
  - `Open3DBroadcast.Transport.MoQ.QueueRefusesNewestUnderBackpressure` pauses the worker, sends 20 frames of 32 KiB into a 256 KiB queue, checks that the first 8 are accepted and the rest refused, then that exactly those 8 reach a receiver through the fake relay, in order.
  - `.AudioIndependentOfFrameQueue` fills the frame budget behind a paused worker, then checks that audio and control are accepted and arrive on their tracks.
  - `.StopWhileSending` is the Verification Stop-under-load case: 1,000 connected cycles with four send threads and an audio thread.
  - None needs a relay, so none is gated by `O3DB_NETWORK_TESTS`.
