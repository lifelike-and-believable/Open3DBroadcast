# 0008: Sender pipeline threading

- **Status:** Accepted (maintainer sign-off 2026-09-29)
- **Accepted with defaults:** every open question below was accepted with the recommended default given next to it. Needs-verification items stay open and are resolved in the implementing WPs; a result that invalidates a default is handled by a superseding ADR.
- **Date:** 2026-09-29
- **Plan decision:** D5 in [`plugin-hardening-and-fab-readiness.md`](../roadmap/plugin-hardening-and-fab-readiness.md) §3
- **Related:** [ADR 0005](0005-wire-resync-and-loss-contract.md) (pull-based descriptor, `StreamWriter`, full-sync policy, new-peer flag), [ADR 0007](0007-transport-abstraction-and-registry.md) (D4: `SendSerialized` contract, audio sink guard), [ADR 0009](0009-protocol-versioning.md) (D8: clock domains), [ADR 0006](0006-test-module-layout-and-fakes.md); feeds WP-A2, WP-A3, WP-S3

**Recommendation in one line:** the game thread only samples the pose into a pooled, immutable frame and pushes it into a small per-sender queue (default depth 2, drop oldest). A per-sender `UE::Tasks` pipe drains the queue and owns everything stateful: curve filtering, the serializer, the `StreamWriter` (ADR 0005), compression, CRC and `SendSerialized`. The worker never touches a UObject: settings and the skeleton descriptor travel with each frame as immutable snapshots. Capture ticks after the mesh's animation and physics. Pose and audio share one sender clock. Audio keeps its own path from the audio thread straight into the transport queue.

## Context

**Everything runs inline on the game thread today (SND-8).** `TickComponent` (`Plugin/Source/Open3DSender/Private/O3DSenderComponent.cpp:1155-1170`) calls `HandleBoneTransformsFinalized` (`:1133-1152`), which samples bones and curves and broadcasts `OnPoseFrameReady` (`:1151`). The serializer is bound to that delegate with `AddRaw` (`O3DSenderSerializer.cpp:69-70`) and, in the same call stack:
- builds a `SubjectList`, calls `CalcMatrices` and `Serialize` (`O3DSenderSerializer.cpp:330-340`), which runs a bitwise CRC (`src/o3ds/model.cpp:872`; CORE-7 measured 548 µs per serialize for 250 bones plus 250 curves, 413 µs of it CRC);
- copies the result into a new `TArray` (`O3DSenderSerializer.cpp:595-597`) and broadcasts `OnSerializedFrame` (`:599`);
- the component forwards it to `SendSerialized` (`O3DSenderComponent.cpp:363-385`).

What `SendSerialized` costs depends on the transport: UDP calls `SendTo` under a lock (TRB-20) and WebRTC calls `lk_send_data_ex` inline (ADR 0007, Context table).

**The serializer reads the component directly (SND-22).** It holds a raw `UO3DSenderComponent*` (`O3DSenderSerializer.h`, member `Component`) and reads its UPROPERTYs every frame (`O3DSenderSerializer.cpp:298-304`, `:436-444`, `:467`, `:566-570`). A worker thread cannot do that.

**Allocation per frame (SND-9, CORE-18).** A new `FO3DSPoseFrame` per capture (`O3DSenderComponent.cpp:969-975`), new filtered curve arrays (`:1124-1128`), a new `SubjectList` in legacy mode, a `std::vector<char>` and a second copy into `TArray` (`O3DSenderSerializer.cpp:339`, `:595-597`).

**Tick ordering (SND-12).** The constructor sets only `bCanEverTick` (`O3DSenderComponent.cpp:60`); there is no tick group and no prerequisite on the target mesh. The comments at `:744` and `:1159` say the bone-transforms-finalized callback was removed in 5.4, but a third-party mirror of the UE 5.7 API lists `USkeletalMeshComponent::RegisterOnBoneTransformsFinalizedDelegate` (References; **needs-verification**, Q2).

**Clocks (SND-17).** Pose frames are stamped with `FPlatformTime::Seconds()` at serialization time (`O3DSenderSerializer.cpp:339`, `:394`, `:512`), not at sampling. Submix audio uses the mixer's `AudioClock` (`O3DSenderAudioCaptureComponent.cpp:25-32`); microphone audio uses the device `StreamTimeSec` (`:309-313`).

**Audio already runs off the game thread.** The audio capture component calls `SubmitPcm` on the audio render or capture thread (`O3DSenderAudioCaptureComponent.cpp:516`). Device enumeration still runs on the game thread, several times per start (SND-18).

**Restarts.** `PostEditChangeProperty` stops and restarts capture for most property edits (`O3DSenderComponent.cpp:1178-1230`); `StopCapture` detaches and clears the serializer (`:247-248`) and tears down the transport (`:256`).

**Accepted constraints.**
- ADR 0005 (i): each pose frame carries a `TSharedPtr<const FO3DSSkeletonDescriptor>` and its hash; frames with a missing or mismatched descriptor are dropped, never padded. This "suits D5, whose worker thread cannot call back into the component".
- ADR 0005 (iv), (vi): the serializer owns one `StreamWriter`; the counter is not reset on Stop/Start in a process; a new-peer callback sets an atomic flag consumed by the next frame.
- ADR 0007: `SendSerialized` is thread-safe and non-blocking and takes `FO3DSendPayload&&`, including a `bFullSync` flag; `Stop()` is safe while a send is in flight.

## Decision drivers

1. The game-thread cost per sender stays under the WP-A2 budget: **0.1 ms for a 250-bone, 250-curve subject**.
2. Wire correctness from ADR 0005 is preserved: no skipped `tx_seq`, no stale descriptor.
3. No UObject access and no raw back-pointer off the game thread (review checklist §7 item 2).
4. Latency beats completeness for live mocap: a late frame is worth less than the next one.
5. Scales to many senders (crowds, multiple performers) without one OS thread each.

## Options considered

### Worker mechanism
- **W1. `UE::Tasks::FPipe` per sender (chosen).** Tasks launched into a pipe run one at a time, so serializer state needs no lock, and no OS thread is dedicated per sender. Pipes are lightweight and store no task list (Epic docs, References). Con: shares the task-graph workers with engine work; needs a priority that does not compete with frame-critical tasks (**needs-verification**, Q1).
- **W2. `FRunnable` plus SPSC queue per sender.** Predictable latency, but one OS thread per sender that sleeps about 99 % of the time, plus wake-event plumbing. Kept as the fallback if Insights shows W1 missing the budget.
- **W3. One shared `FRunnable` for all senders.** One slow transport delays every sender. Rejected.

### Queue and back-pressure
- **Q1. Bounded queue of sampled frames, drop oldest (chosen).** Dropping a *sample* before serialization never drops a full sync and never skips a `tx_seq`, because the worker decides full versus update and stamps the sequence. The receiver sees only a missing sample time.
- **Q2. Drop newest.** Keeps stale data and discards fresh data. Rejected.
- **Q3. Unbounded.** Latency and memory grow without limit when a transport stalls. Rejected.

### Where serializer state lives
- **S1. Worker-owned, with per-frame immutable snapshots of settings and descriptor (chosen).**
- **S2. Shared with the game thread under a lock.** Contention and a lock on the game thread every frame. Rejected.

## Decision

**1. Game thread: sample only.** Per tick, in this order, and nothing else:
1. Rate gate with the accumulator limiter (SND-5, WP-S3) and `EnsureSkeletonCache`.
2. Take a frame from the pool (item 4). Fill `CaptureTimeSec = FPlatformTime::Seconds()` **at sampling** (item 7), the frame index, the subject `FName`, local bone transforms (SND-29: read the bone-space pose when WP-A2's measurement shows it matches), and **raw** curve values in descriptor order.
3. Attach the current `TSharedPtr<const FO3DSSkeletonDescriptor>` and its hash (ADR 0005 i), and the current `TSharedRef<const FO3DSenderEncodingSettings>` (item 6).
4. Push to the sender's pipeline (item 3) and return.
- Curve **filtering** (include/exclude patterns, epsilon; `O3DSenderCurveProcessor`) moves to the worker. Curve **capture** stays on the game thread, because it reads the mesh.
- `OnPoseFrameReady` still fires on the game thread with the sampled frame.
- The transport's `Tick` stays on the game thread (ADR 0007 contract).

**2. Worker: everything stateful.** A pipe task drains the queue. For each frame, it:
- drops it with a rate-limited warning if its descriptor is missing or mismatched (ADR 0005 i);
- applies curve filtering;
- asks the serializer, which owns the per-subject caches, the persistent `O3DS::Subject`s, one `StreamWriter` and a reusable `FlatBufferBuilder` and output buffer (CORE-18), for a full sync or an update per the ADR 0005 (ii) policy;
- serializes, stamps `tx_seq`/`tx_wallclock_us`/`frame_epoch`/`ref_seq` through `StreamWriter`, and computes the CRC (table-driven, CORE-7);
- calls `SendSerialized(FO3DSendPayload&&)` on a `TSharedPtr<IOpen3DSender>` the pipeline holds;
- if a **full sync** comes back `DroppedBackpressure`, marks the subject NeedFull so the next frame is a full sync (ADR 0007 item 3).

`OnSerializedFrame` is kept for C++ listeners but now fires **on the worker thread**, and its comment says so. No listener exists in the repository (grep). It is not Blueprint-exposed (`O3DSenderComponent.h:261`).

**3. The pipeline object.** `FO3DSenderPipeline` (Open3DSender, private) is created once per component and held in a `TSharedPtr` that every launched task captures, so tasks never outlive their state. It contains:
- `UE::Tasks::FPipe` named `O3DSenderPipe_<Subject>`;
- a bounded queue of `TSharedPtr<const FO3DSPoseFrame>` plus **control items** (Start with epoch, Stop, NewTransport, SettingsChanged). Control items are never dropped;
- an atomic "drain task scheduled" flag. The game thread launches a drain task only when the flag was clear (a single compare-exchange); the task re-checks the queue before clearing it;
- the queue itself is either a lock-free SPSC ring or a mutex held only for pointer moves. Either is acceptable; the PR measures both and states which it chose.

**Depth:** default **2 frames**, console variable `o3d.Sender.PipelineDepth` (clamp 1 to 8). On overflow the oldest *pose* frame is released to the pool and `Stats.PipelineDropped` increments. Rationale: at 60 Hz, 2 frames is 33 ms of slack, enough to absorb a hitch without adding standing latency.

**Priority:** `ETaskPriority::BackgroundHigh`, so the work does not compete with foreground frame tasks (**needs-verification** of the 5.7 enum and its scheduling semantics, Q1).

**4. Frame pool.** `FO3DSPoseFramePool` per pipeline hands out frames whose arrays keep their capacity (`Reset()`, not reallocation). Capacity is depth plus 2. A frame is immutable once pushed; the worker holds it as `const` and returns it to the pool when done. This removes the per-frame `FO3DSPoseFrame` and array allocations (SND-9).

**5. Descriptor, full-sync and new-peer requests reach the worker as data.**
- **Descriptor:** on every frame (ADR 0005 i); the worker compares hashes.
- **Rename:** the frame's subject name differs from the cached one; the worker treats it as ADR 0005's "rename" trigger.
- **Start/Stop:** control items. Start carries the new epoch (`max(NewSessionEpoch(), previous + 1)`, ADR 0005 iv). Stop clears caches and marks every subject NeedFull. The `StreamWriter` lives in the pipeline, which survives Stop/Start, so the counter keeps increasing as 0005 requires.
- **New peer:** the transport callback sets an atomic flag on the pipeline (ADR 0005 vi); the next frame on the worker consumes it.
- **Periodic full sync:** evaluated on the worker from `CaptureTimeSec` (monotonic), so a stalled worker does not cause a burst of full syncs.

**6. Property changes during capture: snapshot semantics.**
- Encoding settings (mode, residual predictor, keyframe interval, thresholds, quantization ranges, curve patterns, `FullSyncIntervalSeconds`) are copied into an immutable `FO3DSenderEncodingSettings` on the game thread whenever a relevant property changes (`PostEditChangeProperty`, Blueprint setters, `PostLoad`). Frames carry the current snapshot, so each frame is encoded with exactly one consistent set of settings (SND-14).
- A change of encoding **mode**, curve patterns or quantization ranges forces a full sync on the next frame.
- Transport name or transport options still restart capture, as today (`O3DSenderComponent.cpp:1226-1229`). The restart goes through Stop and Start control items, so it needs no wait.
- The serializer stops holding `UO3DSenderComponent*` (SND-22). This is the first step of WP-A3's split.

**7. One clock domain (SND-17).** Defined in ADR 0009, applied here:
- The **sender clock** is `FPlatformTime::Seconds()`: monotonic and process-relative. Pose `SubjectList.time` is the sampling time on this clock.
- Audio timestamps are mapped onto the same clock. At stream start the sink records `Offset = FPlatformTime::Seconds() - SourceClock` (source clock is `AudioClock` or `StreamTimeSec`) and stamps `SourceClock + Offset`. The offset is re-estimated with a slow low-pass filter so audio-device drift does not accumulate. A jump of more than 100 ms resets it.
- `tx_wallclock_us` stays UTC at transmit (ADR 0005, `StreamWriter`); receivers use it only to estimate clock offset.
- Engine timecode (`FApp::GetTimecode`) is not used in v1 (Q4).

**8. Audio path.** Audio does **not** go through the pose pipe. It arrives on audio threads, and the ADR 0007 sink guard encodes it into sink-local scratch and enqueues it on the transport's send queue. The two paths meet only in the transport queue, where audio items are never dropped to make room for mocap (ADR 0007 item 7). Audio device enumeration is cached and refreshed on demand. It runs once per `StartCapture` and never from `GetOptions` callbacks. Opening the device is done once per start (SND-18).

**9. Tick ordering (SND-12).** `PrimaryComponentTick.TickGroup = TG_PostUpdateWork`, and `BindToTarget` calls `AddTickPrerequisiteComponent(TargetMesh)` (removed in `UnbindFromTarget`). This samples after animation evaluation and after physics blending (**needs-verification** of both APIs and of the 5.7 guarantee that parallel animation evaluation has completed by then, Q2). If `RegisterOnBoneTransformsFinalizedDelegate` is verified to fire on the game thread after physics blending, WP-A2 may bind to it instead and must say so in the PR.

**10. Stop, EndPlay and flush semantics.** `StopCapture` **discards** queued, unserialized pose frames: they are stale by definition. It does not wait for the in-flight task.
- The game thread pushes a Stop control item, stops the transport (ADR 0007: `Stop()` is safe while a send is in flight), and releases its references.
- A task still running holds the pipeline and the transport by `TSharedPtr`; its last `SendSerialized` returns `NotRunning`.
- Frames already handed to the transport follow the transport's own `Stop()` semantics.
- `Open3DSender`'s `ShutdownModule` waits for all pipes to empty, with a 1 s cap and an error log on timeout (**needs-verification** of `FPipe::WaitUntilEmpty` or its 5.7 equivalent, Q1).

**11. Measurement plan (WP-A2 acceptance).**
- Trace scopes: `O3D.Sender.Sample` (game thread), `O3D.Sender.Pipeline.Serialize`, `O3D.Sender.Pipeline.Send` (worker), `O3D.Transport.Worker` (ADR 0007).
- Test scene: one 250-bone, 250-curve subject at 60 Hz, then 10 such senders, on Loopback and on UDP.
- Record in the PR, before and after, from Unreal Insights: game-thread time per sender (median, p99); worker time per frame; capture-to-`SendSerialized` latency; pipeline and transport drop counts.
- **Budgets:** game thread ≤ 0.1 ms median per sender; worker serialize ≤ 0.2 ms per frame after the CORE-7 table CRC; capture-to-send latency p99 ≤ 2 frames at 60 Hz; zero pipeline drops in steady state.
- Core benchmark (`perf.cpp`) Serialize+Parse improves at least 3x (CORE-7).

## Consequences

- **Easier:** encoding cost leaves the game thread; slow transports can no longer stall the frame; the serializer becomes testable without a UObject (feeds WP-A3); the ADR 0005 state machine has one owner on one thread.
- **Harder:** one more thread boundary to reason about; `OnSerializedFrame` listeners must be thread-safe; tests need to wait for the pipe (0006: poll with a timeout, never sleep).
- **Constrains:** transports must honour ADR 0007's non-blocking, thread-safe `SendSerialized`, and UDP and WebRTC need their shared worker before this lands with them (WP-A1 step 4). WP-S3's descriptor-on-frame work is a prerequisite.

## Implementation outline

1. **WP-S3 (prerequisite, per ADR 0005):** descriptor pointer and hash on `FO3DSPoseFrame`; drop on mismatch.
2. **WP-A2a (still synchronous):** `FO3DSenderEncodingSettings` snapshot; the serializer loses `Component`; curve filtering moves after sampling; frame pool; sampling-time clock (`O3DSenderComponent.h/.cpp`, `O3DSenderSerializer.h/.cpp`, `O3DSenderCurveProcessor.cpp`). A pure refactor: WP-S3 tests pass unchanged.
3. **WP-A2b:** tick group and prerequisite (`O3DSenderComponent.cpp` constructor, `BindToTarget`, `UnbindFromTarget`).
4. **WP-A2c:** `FO3DSenderPipeline` with the pipe, queue, control items and `SendSerialized(FO3DSendPayload&&)` (new `Private/O3DSenderPipeline.h/.cpp`; `O3DSenderComponent.cpp:363-385` replaced; `O3DSenderTransportController.cpp` hands the sender to the pipeline). Behind a console variable `o3d.Sender.AsyncPipeline` (default on) for one release, so a regression can be isolated.
5. **WP-A2d:** audio clock mapping and cached device enumeration (`O3DSenderAudioCaptureComponent.cpp`, `O3DSenderComponent.cpp:409-422`, `:485-498`, `:629-650`).
6. **WP-A2e:** CORE-7 table CRC and CORE-18 builder reuse in `src/o3ds/model.cpp` (core PR, CTest benchmark).
7. Remove the `o3d.Sender.AsyncPipeline` fallback one release later.

## Verification / acceptance

- The Insights numbers in Decision §11 are recorded in the WP-A2c PR and meet the budgets.
- Tests (0006 test module): a scripted slow fake transport shows pipeline drops of the *oldest* frames and no gap in `tx_seq`; Stop/Start and rename under load produce correct descriptors (ADR 0005 acceptance); changing quantization ranges mid-capture forces exactly one full sync; destroying the component with a task in flight is clean under ASan (1,000 cycles).
- A review check finds no UObject pointer or `TWeakObjectPtr` dereference in `FO3DSenderPipeline` or `FO3DSenderSerializer`.
- With the tick-order change, a test that moves the root bone each frame shows the captured transform equals the same frame's evaluated pose.

## Addendum: implementation notes (WP-A2a, 2026-10-03)

- **Status:** outline item 2 is implemented. Capture is still synchronous: sampling, curve filtering, serialization and `SendSerialized` run on the game thread, in `TickComponent`, in that order. No pipe, queue or worker (WP-A2c), no tick-group change (WP-A2b), no audio change (WP-A2d), no core change (WP-A2e). The WP-S3 tests pass unchanged (not edited). `O3D_TRANSPORT_API_VERSION` stays 5: the transport interface did not change.
- **What landed.**
  - **Snapshot (item 6).** `FO3DSenderEncodingSettings` now holds everything the curve filter and the serializer read from the component: the encoding fields WP-S3 put there, plus the curve filtering settings (morph clamp, NaN handling, filtering switch, value-filter switch, epsilon, delta, logging, and the include and exclude patterns as `TSharedPtr<const TArray<FString>>`). `UO3DSenderComponent::UpdateEncodingSnapshot` fills it on the game thread for each sampled frame.
  - **Serializer without a component (SND-22).** `Attach`/`Detach`, the raw `UO3DSenderComponent*` and the `OnPoseFrameReady` subscription are gone. The component calls `SerializePoseFrame(Subject, Frame)` after filtering. The serializer reads only the frame (descriptor, filtered curves, `Encoding`, `CaptureTimeSec`); it has no UObject pointer or `TWeakObjectPtr`, and its header no longer names the component class. Instances register for `o3ds.Sender.DumpStats` in the constructor (the list is guarded by a lock); `SetStatsLabel` replaces the component name in that output.
  - **Curve filtering after sampling (item 1).** `FO3DSenderCurveProcessor` now only captures: it builds an immutable `FO3DSCurveList` (names in capture order plus a morph bit per curve) when its cache refreshes, and samples raw values into `FO3DSPoseFrame::RawCurveValues`. The frame carries the list as `FO3DSPoseFrame::CurveList`. The new `FO3DSenderCurveFilter` (same files, private) applies the unchanged rules to the frame with the frame's settings and writes `CurveNames`/`CurveValues`. It keeps the last-sent values and detects a new curve list by pointer, which resets that state as the old in-place cache refresh did.
  - **Frame pool (item 4).** `FO3DSPoseFramePool` (public header, so tests construct it). `FO3DSPoseFrame::Reset()` keeps the capacity of every array and string. The pool is bounded: at most `Capacity` frames exist (default 4 = default depth 2 + 2). `Acquire()` and `Release()` take a lock held only to move a pointer, so WP-A2c can release frames from its worker.
  - **Sampling-time clock (item 7, open question 4 default).** The serializer writes `Frame.CaptureTimeSec` (`FPlatformTime::Seconds()` taken in `HandleBoneTransformsFinalized` before sampling) as the wire time and passes it to `OnSerializedFrame`. It used to read `FPlatformTime::Seconds()` again at serialization. No timecode. The drop-warning rate limit still uses the current time: it is about logging, not the frame.
- **Deviations.**
  1. **The frame carries the snapshot by value, not as `TSharedRef<const FO3DSenderEncodingSettings>`** (item 1.3). WP-S3's tests build frames with `Frame.Encoding = Settings` and read `Frame.Encoding.Mode`, and they must pass unchanged. A value costs nothing extra here: the struct is a few scalars plus two shared pointers, so the per-frame copy allocates nothing and two frames still share one pattern array. WP-A2c can switch to a shared reference if a measurement says so; the tests would then change in that PR.
  2. **The snapshot is refreshed for every sampled frame, not only on property changes** (item 6 names `PostEditChangeProperty`, Blueprint setters and `PostLoad`). The properties are `BlueprintReadWrite`, so Blueprint (and C++) can write them with no notification; refreshing on edit events alone would miss those writes, which the current per-frame read honours. The refresh copies a few scalars and compares the pattern lists case-sensitively (as the matcher does); it allocates only when a list changed.
  3. **Filtering still runs before `OnPoseFrameReady`**, so the delegate keeps seeing filtered curves, as before this PR. Item 1 has the delegate fire with the sampled frame while filtering moves to the worker; with the raw values now on the frame (`CurveList`, `RawCurveValues`), WP-A2c decides what listeners see and records it.
  4. **The subject name is on the frame, not in the snapshot.** It is sampled with the pose (`FO3DSPoseFrame::Subject`), as item 1.2 describes, and the serializer already takes it from there.
  5. **Pool exhaustion skips the sample.** Item 4 sizes the pool but does not say what the game thread does when every frame is out. `Acquire()` returns null and the component skips that sample (Verbose log); it cannot happen while capture is synchronous. WP-A2c's drop-oldest returns a queued frame to the pool before that point.
  6. **`o3ds.Sender.DumpStats`** lists every live serializer, including ones tests construct, because registration moved from `Attach` to the constructor. Reading another instance's stats is still unsynchronised with that instance's serialization; that matters once serialization leaves the game thread, so WP-A2c must either stop the dump from reading worker state or copy the counters under the pipeline.
- **UE API verification.** The UE 5.7 source mirror (lifelike-and-believable/UnrealEngine) was not reachable from this session (the GitHub connector refused the repository), so no new signature was checked there. Instead the change uses only UE APIs that this plugin already compiles against 5.7 in CI, with the same call forms:
  - `TArray::Pop(EAllowShrinking::No)` (`O3DSinkAudioEncoder.cpp`), `TArray::SetNumZeroed`, `Reset`, `Reserve`, `Max` (`O3DSenderCurveProcessor.cpp`, existing tests);
  - `TBitArray<>` with `Init`, `IsValidIndex` and `operator[]` (`O3DSenderCurveProcessor.h`, unchanged include `Containers/BitArray.h`);
  - `FCriticalSection` with `FScopeLock(&Lock)` (`HAL/CriticalSection.h`, `Misc/ScopeLock.h`, as in `O3DTransportRegistry.cpp`);
  - `TUniquePtr`/`MakeUnique`, `TSharedPtr<const T>` from `MakeShared<T>` (as `DescriptorSnapshot` does), `IConsoleManager::RegisterConsoleCommand` and `FPlatformTime::Seconds()` (all previously in these files);
  - `UObjectBaseUtility::GetPathName()` for the stats label.
  FString's `Reset()` keeps the allocation (documented behaviour since UE 4). No new UObject, tick, task or audio API is used.
- **Thread notes for WP-A2c.** After sampling nothing reads the component: the filter and the serializer work from the frame, which owns or shares (immutably) everything they read. `OnSerializedFrame` still fires on the game thread in this PR; its comment now says it fires on the thread that calls `SerializePoseFrame`. The component still owns the serializer, the filter and the pool; WP-A2c moves them into `FO3DSenderPipeline`.
- **Tests (0006 test module).**
  - `Open3DBroadcast.Sender.EncodingSnapshot.SerializerWorksWithoutComponent`: a standalone serializer encodes from the snapshot; a frame sampled from a component keeps its settings after the component's properties change; an unchanged pattern list is shared, not copied.
  - `Open3DBroadcast.Sender.FramePool.ReusesFramesAndIsBounded`: the same frame comes back reset with its allocations, the pool never holds or hands out more than its capacity, and a foreign frame is not kept.
  - `Open3DBroadcast.Sender.CurveFilter.AfterSamplingMatchesBefore`: a sequence covering morph clamp, NaN, an exclude pattern, epsilon and delta, a return to zero, filtering off and a new curve list gives the values the pre-WP-A2a filter gave (worked out from its code at 5ee5ac6), and the receiver gets exactly those curves.
  - `Open3DBroadcast.Sender.Wire.SerializedTimeIsSamplingTime`: in every encoding, full syncs and updates carry the sampling time on the wire and in `OnSerializedFrame`.

## Addendum: implementation notes (WP-A2b, 2026-10-03)

- **Status:** outline item 3 is implemented. Capture is still synchronous on the game thread, as after WP-A2a. No pipe, queue or worker (WP-A2c), no audio change (WP-A2d), no core change (WP-A2e). `O3D_TRANSPORT_API_VERSION` stays 5: the transport interface did not change. - **What landed (item 9).**
  - The constructor sets `PrimaryComponentTick.TickGroup = TG_PostUpdateWork`.   - `BindToTarget` makes the target mesh's tick a prerequisite of the sender's tick (`AddTickPrerequisiteComponent`); `UnbindFromTarget` removes it (`RemoveTickPrerequisiteComponent`). At most one mesh is a prerequisite at a time; binding the bound mesh again adds nothing; unbinding when nothing is bound does nothing. Prerequisites added by other code are left alone.

  - The comments that said `RegisterOnBoneTransformsFinalizedDelegate` was removed in UE 5.4 are gone: that claim was never verified (see below). The delegate is not used.

## Addendum: implementation notes (WP-A2c, 2026-10-03)

- **Status:** outline item 4 is implemented. Sampling stays on the game thread in the component's tick (`TG_PostUpdateWork`, after the target mesh, WP-A2b); curve filtering, serialization and `SendSerialized` run on a per-sender worker task. The transport's `Tick`, `TickControl` and `SendControl` stay on the game thread (ADR 0007, ADR 0011). No audio change (WP-A2d), no core change (WP-A2e). `O3D_TRANSPORT_API_VERSION` stays 5: the transport interface did not change; `SendSerialized` was already documented as "any thread; thread-safe; never blocks" (ADR 0007 item 3), and that contract is what the worker relies on. Existing tests pass unchanged (none was edited; one white-box accessor, `FO3DSenderComponentTestAccess::HasSerializer`, now checks the pipeline that owns the serializer).
- **What landed.**
  - **`FO3DSenderPipeline`** (`Open3DSender/Private/O3DSenderPipeline.h/.cpp`), one per component, created by the first `StartCapture`, kept across Stop/Start, dropped at `EndPlay` (as the serializer was before). It owns the frame pool, the curve filter (moved out of the component), the serializer, the queue and a `TSharedPtr<IOpen3DSender>`. It is held by `TSharedPtr`; every drain task captures one, so the owner can let go at any time and the last reference may be dropped on the worker. Nothing in it reads a UObject or a `TWeakObjectPtr`; the only pointer into the component is the address of its `OnSerializedFrame` delegate (see "Stop and destruction").
  - **Worker.** A `UE::Tasks::Launch` task with `ETaskPriority::BackgroundHigh`, launched when the queue goes from idle to busy. The "drain task scheduled" flag of item 3 (one compare-exchange) allows one task at a time; the task drains the queue, clears the flag, and re-checks the queue before it ends, taking the flag back if an item slipped in. Each item is processed under a `WorkerLock`, one item per lock hold.
  - **Queue.** One FIFO (`TArray`, a mutex held only for pointer moves; deviation 7) of pose frames and control items (`Start`, `Stop`, `RemoveSubject`). Depth `o3d.Sender.PipelineDepth` (default 2, clamped 1 to 8). When a frame arrives and more than the depth are waiting, the oldest waiting frame goes back to the pool and `FO3DSenderPipelineStats::FramesDropped` grows. Control items are never dropped.
  - **Control items (SND-1).** `Start` resets the curve filter (as `StartCapture` did). `Stop` clears the serializer caches and the curve filter, so every subject's next frame is a full sync. `RemoveSubject` carries a rename (`EnsureSubjectNameCached`) and the purge in `StopCapture`, in order with the frames already queued, so the new name always starts with a full sync and no frame under the old name follows it. Settings changes need no item: each frame carries its settings snapshot (item 6), and the serializer's fingerprint forces a full sync when the mode or the quantization ranges change.
  - **Send.** The worker moves the serializer's buffer into `FO3DSendPayload` (no copy; the old path copied it), sets `bFullSync`, and, when a full sync comes back `DroppedBackpressure`, calls the new `FO3DSenderSerializer::RequestFullSync(Subject)` so the next frame is a full sync (item 2). `FO3DSenderSerializer::SerializePoseFrameTo` returns the bytes and the full-sync flag; `SerializePoseFrame` keeps its signature and calls it.
  - **`OnSerializedFrame`** (open question 5 default): kept; fires on the worker while `o3d.Sender.AsyncPipeline` is on, documented on the delegate (worker thread, thread-safe listeners only, bind and unbind only while capture is stopped). The pipeline broadcasts it between serialization and the send, as `HandleSerializedFrameForward` did; that function is gone.
  - **`OnPoseFrameReady`** (the A2a open item): fires on the game thread with the sampled frame, before it is handed over, as item 1 says. With the pipeline on, filtering runs later on the worker, so listeners see raw curves (`CurveList`, `RawCurveValues`) and empty `CurveNames`/`CurveValues`. With it off they see the filtered curves, as in WP-A2b.
  - **Console variable `o3d.Sender.AsyncPipeline`** (default 1), read at `StartCapture` and latched for that session. At 0 every item is processed on the game thread inside the call, in the WP-A2b order (filter, `OnPoseFrameReady`, serialize, `OnSerializedFrame`, send). Items an earlier asynchronous session left queued are processed first, so switching between sessions keeps the order.
  - **Stop and destruction (item 10).** `StopCapture` discards the queued frames (`FramesDiscardedOnStop`) and pushes `Stop`; it does not wait for queued work or the network. Two calls wait for at most one item the worker is processing (deviation 3): removing the `OnSerializedFrame` listener (`StopCapture`, `EndPlay`, the component's destructor), and detaching the transport sender, which `FO3DSenderTransportController::Stop` now does before it stops the sender. After either returns the worker never touches that object again. The component destructor detaches both, so a component garbage-collected with a task in flight leaves the task nothing of its own to reach. `Open3DSender`'s `ShutdownModule` waits up to 1 s for running drain tasks and logs an Error naming the count on timeout (a global atomic counter, deviation 1).
  - **Transport hand-off.** `FO3DSenderTransportController::SetPipeline`; a started sender is attached with `AttachSender` and detached in `Stop` before `IOpen3DSender::Stop`. This replaces a `NewTransport` control item (deviation 4).
  - **Stats and timing.** `FO3DSenderPipelineStats` (`Open3DSender/Public/O3DSenderPipelineStats.h`), from atomics: submitted, dropped, discarded on stop, processed, handed to the transport, accepted, refused, without a transport, last send sequence, queued and maximum queued frames, last and largest worker time per frame, last and largest capture-to-`SendSerialized` latency, mode. `UO3DSenderComponent::GetPipelineStats()` returns them; `o3d.Sender.DumpPipelineStats` logs them for every live pipeline. Trace scopes (item 11): `O3D.Sender.Sample` (game thread, around sampling; in synchronous mode it also encloses the filter, serialization and send, which makes it the before/after number), `O3D.Sender.Pipeline.Serialize` (worker, one frame including the send) and `O3D.Sender.Pipeline.Send`.
  - **`o3ds.Sender.DumpStats` (A2a deviation 6).** `FO3DSenderSerializer` has a recursive `StateLock`; every member function takes it, including `DumpStatsInstance`, so the dump reads a serializer while its worker serializes without a race. The dump holds the instance list lock and then each instance's lock, so an instance cannot be destroyed while it is read. `OnSerializedFrame` (the serializer's) fires with the lock held; its comment says what a listener must not do.
- **Deviations.**
  1. **`UE::Tasks::Launch` plus the item 3 flag, not `UE::Tasks::FPipe`.** The flag already makes the tasks of one pipeline run one at a time, which is what the pipe was for. The pipe adds a lifetime hazard this design cannot rule out without the 5.7 source: `FPipe`'s destructor checks that it has no work, and, as far as is known from earlier engine versions, a piped task's body (with its captures) is destroyed before the task clears itself from the pipe. A pipe owned by the pipeline, which the task keeps alive, could then be destroyed by the task's own last reference and touched afterwards. With plain tasks the task object is the task system's, and dropping the pipeline inside the body is safe. `FPipe::WaitUntilEmpty` (needs-verification in Q1) is not used; `WaitForIdle` (an event with a timeout, for tests) and `WaitForAllIdle` (a global counter of scheduled or running drain tasks, for `ShutdownModule`) replace it. Open question 1's default (W1) stands in substance: tasks on the task graph, no thread per sender; the W2 fallback is still available if Insights shows a miss.
  2. **No `tx_seq` on the wire yet.** `O3DS::StreamWriter` (ADR 0005) does not exist: it is WP-A4a, a core change, out of scope here. The core's `Subject::Serialize` and `Subject::SerializeUpdate`, which the persistent encodings use, take no sequence parameters, so stamping `tx_seq` in some encodings only would be inconsistent. The pipeline keeps `LastSendSequence`, incremented on the worker for each payload at the moment it is handed to `SendSerialized`, which is where `StreamWriter` will stamp `tx_seq` when WP-A4a lands. The `Start` item carries no epoch for the same reason. The slow-transport test checks the property the ADR's argument rests on: frames are dropped only before serialization, every serialized frame reaches `SendSerialized` in order, the send sequence has no gap, and a receiver applies every update.
  3. **Stop waits for one item in flight.** Item 10 says `StopCapture` does not wait for the in-flight task and that a late `SendSerialized` returns `NotRunning`. Here `StopCapture` (and `EndPlay`, the destructor and the controller's `Stop`) waits for the item the worker is processing, never for queued items or the network. Reasons: the worker broadcasts the component's `OnSerializedFrame`, so the component must know it is no longer called before it can be destroyed; the registry's unregister drain (ADR 0007 item 5, `Open3DBroadcast.Shared.TransportLifetime.SenderComponentReleasesOnUnregister`) expects the sender released when the controller stops; and the WebRTC sender is not safe against a `Stop` concurrent with `SendSerialized` (below). The wait is bounded by one serialize plus one `SendSerialized`, which ADR 0007 requires to be non-blocking. If `lk_send_data_ex` turns out to block, the game thread would wait for it on stop.
  4. **No `NewTransport` or `SettingsChanged` control items.** The sender is attached and detached directly under the worker lock (deviation 3 needs a synchronous detach anyway), and settings travel on every frame.
  5. **The frame still carries the settings by value** (A2a deviation 1); no measurement asked for a shared reference.
  6. **New-peer flag (item 5)** is not implemented: `SetPeerJoinedCallback` is deferred to WP-A4b (ADR 0007 addendum, PR 3). The worker-side hook exists (`RequestFullSync`).
  7. **Queue implementation.** Item 3 asks the PR to measure an SPSC ring against a mutex held for pointer moves. Only the mutex version exists and nothing was measured (no engine in this session). The lock is taken twice per frame (push on the game thread, pop on the worker) and never across serialization.
  8. **Pool capacity** is `MaxDepth + 2` (10), not depth + 2, because the depth is a console variable that can change at run time. The pool allocates lazily, so a steady capture at depth 2 still holds at most four frames: one sampling, two waiting, one on the worker.
  9. **The mode is latched at `StartCapture`.** Flipping `o3d.Sender.AsyncPipeline` during capture takes effect at the next start.
  10. **Synchronous without worker threads.** When `FPlatformProcess::SupportsMultithreading()` is false (for example `-nothreading`), the pipeline runs synchronously whatever the console variable says: nothing waits for a drain task, so a task that only runs when waited for would never send.
- **Transport thread safety (`SendSerialized` from the worker).**
  - Loopback, TCP, UDP, NNG and MoQ (WP-A1 step 4): `SendSerialized` checks atomic running flags (MoQ: `FThreadSafeBool`) and enqueues on `FO3DSendQueue`; safe from any thread. Loopback's `bInitialized` is a plain bool and `Channel` a plain `TSharedPtr`, both written in `Initialize`, before the controller attaches the sender (the attach takes the worker lock, which orders them), and not changed by `Stop`.
  - WebRTC add-on: **not safe on its own against a concurrent `Stop`.** `FO3DWebRTCSender::SendSerialized` reads `ClientHandle` without entering the lifetime gate that `SendControl` and the audio sinks use, and calls `lk_send_data_ex` synchronously; `Stop` destroys the client. Through the pipeline this cannot race, because the controller detaches the sender (waiting for a send in flight) before it calls `Stop`. Another caller would need the gate, which belongs to the WebRTC add-on (HANDOFF leftovers).
  - `SendControl` is unchanged: the control publisher calls it on the game thread (ADR 0011 v1).

- **Status:** outline item 5 is implemented: the clock mapping of item 7 for audio and the device handling of item 8. Audio still does not go through the pose pipeline (item 8). - **What landed: clock (item 7, SND-17).**
  - `FO3DAudioClockMapper` (`Open3DSender/Public/O3DAudioClockMapper.h`, header-only, no UObject): `Map(SourceSec, NowSec)` returns `SourceSec + Offset`. The first buffer sets `Offset = Now - Source`. Afterwards the offset follows `Measured - Offset` through a first-order low-pass filter with a 5 s time constant measured in source-clock seconds (`alpha = 1 - exp(-dSource / 5 s)`), so the buffer size does not change the filter.
  - Each producer (`FO3DSenderAudioProducerState`: one per submix tap, one per opened microphone stream) owns one mapper. The submix tap maps `AudioClock`, the microphone callback `StreamTimeSec`, each against `FPlatformTime::Seconds()` read in the callback. Tap and microphone producer are created per start, so every start begins with a fresh offset. Mapping happens before resampling; the resampler's first-frame offset is added to the mapped time as before.
  - Delivery delay is a constant bias: the stamp is when the buffer reached the producer, mapped back through the source clock (about one buffer plus driver latency after the first sample). It is not compensated.
- **Deviations (clock).**
  1. **The 100 ms jump rule is asymmetric.** Item 7 says "a jump of more than 100 ms resets it". A delivery delay (a hitch delaying the audio thread, then a burst of queued callbacks) makes the measured offset larger for a while and then recovers; resetting on it would shift every later stamp by the hitch. So the mapper resets at once when the source clock goes backwards or the measured offset falls more than 100 ms below the estimate (the source got ahead of the sender clock, which a delay cannot cause), and resets when the measured offset stays more than 100 ms above the estimate for 0.5 s of sender time (`PersistSec`), which a lasting change (a stalled source clock) does and a hitch does not. Until then stamps keep the old offset. With these rules stamps do not go backwards (test `DiscontinuitiesReset`).
  2. **`PushFrames` is not mapped.** Its callers choose the timestamp; it is documented as sender-clock time and passed through unchanged. The existing tests push synthetic times in a tight loop (`Sender.Audio.ResampledBuffersAddUp` checks they never go backwards), which a mapper fed with the wall clock would read as discontinuities.
  3. **No console variables** for the time constant, threshold or persistence; they are `static constexpr` members of the mapper.
- **What landed: devices (item 8, SND-18).**
  - `FO3DAudioInputDevices` (`Open3DSender/Public/O3DAudioInputDevices.h`, exported): one process-wide cached list of capture device names, filled by `Refresh()` (one `Audio::FAudioCapture::GetCaptureDevicesAvailable`), read by `GetNames()` and `FindIndex(FName)` (case-insensitive; -1 for None or unknown). A lock guards the list; the enumeration runs outside it.
  - Enumeration runs once per `UO3DSenderComponent::StartCapture` with audio enabled in Input mode (before the transport config and the capture config resolve the device index), once in the editor after engine init (`FCoreDelegates::OnPostEngineInit`, registered in `Open3DSender`'s `StartupModule`), and on request: `UO3DSenderComponent::RefreshAudioInputDevices()` (static, Blueprint-callable) and the console command `o3d.Sender.Audio.RefreshDevices` (logs the list).
  - Everything else reads the cache: both components' `GetOptions` functions (`GetAvailableAudioInputDeviceOptions`, `GetAvailableInputDeviceOptions`), `ResolveAudioDeviceIndex` and `ResolveDeviceIndexFromName`, and through them `SyncAudioConfigSource` in the constructor, `PostInitProperties`, `OnRegister`, `PostLoad`, `BeginPlay` and property edits, which used to enumerate each time in Input mode. The four copies of the enumeration loop are gone.
  - **Opened once per start.** `StartCapture` called `UpdateAudioCaptureBinding` twice (from `InitializeTransport` after the transport started, and again after it returned); each call ran `StartCaptureWithMode`, which closes and reopens the microphone. The call in `InitializeTransport` is removed; `StartCapture`'s call follows it directly and binds the started transport's sink. `UO3DSenderAudioCaptureComponent::BeginPlay` opened the device whenever none was open, including when the sender component creates the capture component during play (registering it runs `BeginPlay`) before the start configured it. It now opens only when a sink is bound; `SetAudioSink` opens the device when it binds a sink on a component that has begun play, has none open, and has not tried to open one since its capture last (re)started (`bMicOpenAttempted`, cleared by `ShutdownMicCapture`), so a failed open is not retried on every bind.
- **Deviations (devices).**
  4. **The editor fills the cache once at startup.** Item 8 says enumeration "runs once per `StartCapture` and never from `GetOptions` callbacks". Without a first fill the editor's device pickers would stay empty until a play session started capture. The fill waits for engine init because `FAudioCapture` uses the first `IAudioCaptureFactory` modular feature, registered by a module that may load after `Open3DSender`. It does not run in commandlets or in a game.
  5. **Hot-plug is not watched.** A device plugged in while the editor runs appears in the picker after `RefreshAudioInputDevices`, the console command, or the next Input start. Each Input start enumerates, so the index it opens comes from a current list.
  6. **Device index, not id.** The capture API opens by index (`FAudioCaptureDeviceParams::DeviceIndex`); the name resolves to the index in the list the same start just enumerated, so a list that changed between starts is handled.
- **UE API verification (local UE 5.7 install).** `Audio::FAudioCapture::GetCaptureDevicesAvailable(TArray<FCaptureDeviceInfo>&)` (returns `int32`), `OpenAudioCaptureStream`, `StartStream`, `StopStream`, `CloseStream` (`Runtime/AudioCaptureCore/Public/AudioCaptureCore.h`); `Audio::FCaptureDeviceInfo::DeviceName` and `FOnAudioCaptureFunction`'s `double StreamTime` (`AudioCaptureDeviceInterface.h`); `ISubmixBufferListener::OnNewSubmixBuffer`'s `double AudioClock`, documented as "from start of audio rendering" (`Runtime/Engine/Public/ISubmixBufferListener.h`); `FAudioCapture::CreateImpl` takes the first `IAudioCaptureFactory` modular feature or falls back to a null device (`AudioCaptureCore/Private/AudioCaptureInternal.h`); `FCoreDelegates::OnPostEngineInit` (`Core/Public/Misc/CoreDelegates.h`); `AddExpectedMessage` with `Occurrences < 0` ignores any number of matches (`Core/Public/Misc/AutomationTest.h`).
- **Tests (0006 test module).**
  - `Open3DBroadcast.Sender.AudioClock.MapsOntoSenderClock`, `.DriftDoesNotAccumulate` (100 ppm for 10 minutes stays within 2 ms), `.JitterBarelyMovesStamps` (0 to 10 ms of delivery jitter moves each step by less than 0.1 ms), `.DiscontinuitiesReset` (a 200 ms hitch does not reset; a source clock going backwards or leaping ahead resets at once; a lasting 300 ms change resets after `PersistSec`; stamps never go backwards). Manual clocks, no sleeps.
  - `Open3DBroadcast.Sender.AudioDevices.LookupsReadTheCache` and `.StartEnumeratesAndOpensOnce`, on a fake device list (`FO3DAudioInputDevices::SetEnumeratorForTesting`). The second starts capture without a world or transport; opening the device is real and counted (`FO3DSenderAudioCaptureTestAccess::GetNumMicOpenAttempts`); a host without a capture device logs a warning the test allows.
  - `Open3DBroadcast.Sender.AudioDevices.SinkBindOpensAtMostOnce`, in a game world (pitfall 26, so `HasBegunPlay` is true): binding and rebinding a sink after a start does not reopen the device; a standalone capture component opens it when a sink is bound and does not retry a failed open on rebind.
  - Every open in these tests fails: `Run-AutomationTests.ps1` starts the editor with `-NoSound`, so `FApp::CanEverRenderAudio()` is false and `FAudioCapture` uses its null device, whose `OpenAudioCaptureStream` returns false without logging (`AudioCaptureInternal.h`). The tests behave the same on every host and never touch a real device.
  - Not tested: the submix tap and the microphone callback themselves; they need a live audio mixer or device, like SND-7 and SND-28 before.
- **Known limit.** A standalone capture component whose sink is cleared and bound again keeps its open device and only stops and restarts the stream; its producer, and so its clock offset, is kept. If the device's stream time pauses while stopped, stamps after the restart are off by the pause until the mapper's 0.5 s persistence resets them. The sender component reopens the device on every start, so it is not affected. Resetting the mapper on `StartStream` would need a guarantee that no capture callback is running after `StopStream` returns, which was not checked.

## Addendum: implementation notes (WP-A2e, 2026-10-03)

- **Status:** outline item 6 is implemented in the core (`src/o3ds`) and mirrored into the plugin. The wire format is unchanged: same header, same CRC value. `O3D_TRANSPORT_API_VERSION` stays 5. No plugin source changed apart from the generated mirror and `Open3DStreamCore.Build.cs`.
- **What landed.**
  - **CRC (CORE-7).** `O3DS::Crc32(const void*, size_t)` (`src/o3ds/crc32.h/.cpp`, `O3DS_API`) computes CRC-32 with CRCpp's `CRC_32()` parameters (reflected, polynomial 0x04C11DB7, init and final XOR 0xFFFFFFFF) by slicing-by-8: eight 256-entry tables built once in a function-local static, words read with `memcpy` (any alignment), a byte loop for the tail and on big-endian hosts. `finalize()` and `SubjectList::Parse()` use it. The core no longer includes `CRC.h`.
  - **Builder reuse (CORE-18, the serialize half).** The six whole-buffer `Serialize*` functions (`Subject::Serialize`, `SerializeUpdate`, `SerializeUpdateResidual` and their `SubjectList` counterparts) take a `thread_local` `FlatBufferBuilder` (initial size 16 KiB) and `Clear()` it; FlatBuffers 2.0.6's `Clear()` keeps the allocation (`vector_downward::clear` only resets the cursor). None of them calls another whole-buffer `Serialize*` (their fallbacks call the builder overloads), so the shared builder is never cleared mid-build. `finalize()` sizes the output once and writes the header and payload with `memcpy` instead of three `back_inserter` copies, so a caller that reuses its `std::vector<char>` stops reallocating.
  - **Benchmark.** `test/bench/serialize_bench.cpp` builds `o3ds_core_bench` (`perf.cpp` from the review, made a CTest entry): full Serialize, Parse, SerializeUpdate with every value moving, and the CRC alone, bitwise against `Crc32`. It checks the round trip and that the header carries the bitwise CRC, and never fails on speed. CTest runs it with 50 iterations (`core.bench.serialize`, label `bench`); the default is 2,000.
- **Numbers (Verification: "Core benchmark Serialize+Parse improves at least 3x").** MSVC 14.44, Release, `-O2` defaults of the CMake Release build, 2,000 iterations, one 250-bone, 250-curve subject (34,768-byte full sync), on the maintainer's workstation; the run with the lowest Serialize + Parse of two runs before and three after (runs vary by about 5 %):

  | | before | after | factor |
  |---|---|---|---|
  | Serialize (full) | 499 µs | 96 µs | 5.2x |
  | Parse (full) | 406 µs | 162 µs | 2.5x |
  | Serialize + Parse | 905 µs | 259 µs | **3.5x** |
  | SerializeUpdate | 81 µs | 14 µs | 5.6x |
  | CRC over 34.7 KB | 278 µs (bitwise) | 16 µs | 17x |

  The review's numbers (CORE-7) were GCC `-O2` on Linux; no GCC number was taken here (no Linux toolchain on this machine). The first step, CRCpp's one-table `Calculate` (61 µs), gave only 2.7x for Serialize plus Parse; slicing-by-8 took it past 3x. The budget "worker serialize at most 0.2 ms per frame after the CORE-7 table CRC" (item 11) is met by the core alone (96 µs for a full sync); the plugin's per-frame number still needs the Insights capture of the WP-A2c addendum.
- **Deviations.**
  1. **Slicing-by-8 instead of CRCpp's table.** The review recommends "a function-static `CRCPP::CRC::Table` ... A better option is a slicing-by-8 or hardware CRC32C". Slicing-by-8 keeps the value; the hardware instruction computes CRC-32C, a different polynomial, which would be a wire change (ADR 0009).
  2. **The CRC is not made optional** (CORE-7's flag-bit idea): it would change the header's meaning, which is ADR 0009's business.
  3. **Parse still re-creates every `Transform` on a full sync** (the Parse half of CORE-18: "diff topology on resync and reuse `Transform` objects", the anchor map, and skipping the second Verifier pass after `PeekMeta`). It changes receiver resync behaviour (`ParsedSubjectInfo::fullDescriptor`, the LiveLink static re-push), so it is left for its own change. Of Parse's 162 µs, the CRC is now 16 µs; the rest is the Verifier, allocation and the hierarchy solve.
  4. **CRCpp leaves the plugin.** No core file includes `CRC.h` any more, so `sync_o3ds_core.py` no longer mirrors it, and now copies the CRC++ licence only while a `crccpp/` file is mirrored; `Open3DStreamCore.Build.cs` drops the `crccpp` include path and `CRCPP_USE_NAMESPACE`; `THIRD_PARTY_LICENSES.md` drops the CRC++ row. The core's CMake build still finds CRCpp for the tests and the benchmark, and the script still records the `thirdparty/crccpp` pin in `SYNC_STAMP.txt`.
  5. **`thread_local` builders.** One builder per thread that serializes, kept for the thread's life and sized by the largest buffer it built (about 35 KB here). The plugin serializes on the pipeline's task-graph workers (WP-A2c), so a few builders exist. A caller-owned builder parameter would avoid the per-thread memory but changes every `Serialize*` signature the plugin calls.
- **Tests.**
  - `core.crc32_tests`: `Crc32_KnownCheckValue` ("123456789" gives 0xCBF43926), `Crc32_MatchesBitwiseForEveryLengthAndAlignment` (lengths 0 to 100 at offsets 0 to 7), `Crc32_MatchesBitwiseForLargeBuffers` (up to 1 MiB, unaligned, all-zero and all-0xFF), `Crc32_SerializedHeaderCarriesBitwiseCrc` (and a reused output vector is rewritten, not appended to).
  - All 23 core CTest entries pass with MSVC Release. The plugin's automation suite passes against the regenerated mirror (429 of 429, UE 5.7, local editor build).

## Addendum: Parse object reuse (WP-A2 follow-up, 2026-10-03)

- **Status:** the Parse half of CORE-18 that the WP-A2e addendum left out (deviation 3). Core only (`src/o3ds/model.cpp`), mirrored into the plugin; wire format and `O3D_TRANSPORT_API_VERSION` (5) unchanged.
- **What changed.** `SubjectList::Parse()` with `clearInactive` (the plugin's call, `O3DReceiverSource.cpp`) no longer deletes the list before the full subjects: the old subjects are set aside, a full subject of the same name takes its object back (reset: joints, curves, reference, error, residual encoder and decoder cleared, which is everything `new Subject(name)` does not set and `ParseSubject()` does not overwrite), and the rest are deleted after the subject loop, before the updates apply, which is where the old code had none of them either. `ParseSubject()` reuses the first transforms in node order (`*t = Transform(parent)`, then the name), deletes the surplus and allocates only new ones; curve names are assigned in place.
- **Why it is invisible to receivers.** With `clearInactive` the old code started every full-subject buffer from an empty list, so its result was by definition that of parsing into a new list. `core.parse_reuse_tests` checks exactly that oracle after every buffer of a sequence chosen to hit each branch (grow, shrink, reorder, drop, duplicate, nameless nodes, curves absent or empty, an update for a dropped subject, a rejected subject, an empty list), including `Parse`'s return value, `mError` and the touched-subject report (`fullDescriptor` stays true for every full subject, so the receiver's LiveLink static re-push is unchanged). Removing two lines of the subject reset makes the suite fail (checked).
- **Numbers.** MSVC Release, `o3ds_core_bench`: Parse about 160 µs to about 85 µs; Serialize + Parse about 190 µs, against about 905 µs before WP-A2e (runs vary by about 5 %).
- **One observable difference:** a resynced subject's `Subject*` and its first `Transform*`s stay the same objects. Nothing in the plugin keeps them across `Parse` calls (it looks subjects up by name each packet), and stable pointers are the safer behaviour for any caller that does.
- **Not done:** skipping the second Verifier pass after `PeekMeta`; it needs a new `Parse` overload and the receiver's call order checked.
